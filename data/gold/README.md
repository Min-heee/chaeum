# 정답 세트

| 파일 | 무엇 |
|---|---|
| `dev.jsonl` | 연습 40건. 고칠 때 보는 세트다 |
| `test.sha256` | 안 여는 세트 60건의 해시(지금은 3판 파일의 것). 파일은 개선 동안 저장소 밖(`SEALED_GOLD_PATH`)에 둔다 |
| (저장소 밖) `real.jsonl` | 실제 자료 20건. 남이 쓴 공개 글이라 원문을 저장소에 넣지 않는다. 안 여는 세트와 같은 폴더에 둔다. 얼린 뒤에 모은다 |
| `real-sources.json` | 실제 자료의 출처 목록: 주소, 받은 날짜, 원문의 꼴, 정답 문서가 됐는지 넘겼는지. 원문도 값도 없다 |
| `real-edits.json` | 실제 자료에서 사람이 칸마다 한 일(그대로·고침·지움·넣음)과 그 셈. 값은 없다 |
| (저장소 밖) `real-intake.jsonl` | 실제 자료를 넣은 기록. 모델이 낸 초안과 칸별 "모델이 낸 값 / 사람이 확정한 값 / 한 일"이 값째로 들어 있다. 그 초안을 만든 호출의 답(장부 줄)도 함께 싣는다 |
| `hand.jsonl` | 손글 10건. 파이프라인을 얼린 뒤에 쓴다. 원문과 정답이 모두 들어 있다 |
| `reviews.jsonl` | 사람이 확인한 기록(판정, 고친 칸 수, 걸린 초). 원문은 없다. 지금 63줄이다. 걸린 초가 빈 줄은 사람이 정한 기준을 도구가 적용한 것이다(아래 3판). 기록 줄에는 누가 적용했는지 적는 칸이 없다. 걸린 초가 빈 것으로만 가린다 |

만드는 순서는 **정답 먼저 → 원문 나중 → 사람 확인**이다.

## 지금은 연습 묶음 2판, 안 여는 세트 3판이다

**2판(goldVersion 2) — 연습 묶음과 안 여는 세트 모두, 측정 전.** 1판의 원문은 값 표기가 판에 박혀 있었다. 연습 40건 가운데 크기는 23건 중 21건이 "가로 Nm × 세로 Nm", 초수와 횟수는 전부 "N초"·"하루 N회", 예약 마감은 23건 중 22건이 "N일 전까지 예약"이었다. 이런 세트로는 "글에서 값을 뽑는 힘"이 아니라 "그 한 가지 표기를 읽는 힘"을 재게 된다. 그래서 2판에서는 **정답 값은 100건 모두 그대로 두고, 값을 적는 표기 꼴과 원문만 다시 썼다.** 같은 크기를 어떤 글은 "8000mm*4500mm"로, 어떤 글은 표 머리에 단위를 밝힌 "8X4.5"로 적는다. 2판 연습 세트에서 한 표기 뼈대가 차지하는 몫은 칸마다 많아야 25%(문서가 3건뿐인 케이터링 운영 시간만 3건 중 1건)이고, 네 글자 토막이 15% 넘게 겹치는 글 짝은 100건 가운데 8쌍에서 0쌍이 됐다. 사람 확인 기록이 0건일 때 바꿨으므로 잃은 확인은 없다. 1판의 안 여는 세트 파일은 저장소 밖에 `test.v1.jsonl` 로 남겨 두었다.

**3판(goldVersion 3) — 안 여는 세트만, 2026-10-13 최종 측정 뒤.** 사람이 기준을 하나 정했다: 배달 도착 시간은 운영 시간이 아니다. 그 기준으로 세 문서(test-019, test-024, test-033)의 케이터링 운영 시간 칸이 "없음"이 됐다. 기준은 사람이 정했고(다시 본 문서는 test-019·test-024 둘이다), 같은 꼴 한 건(test-033)은 AI가 찾았고, 적용은 AI 도구가 확인 화면과 같은 저장 함수로 했다. 사람이 손으로 누른 것이 아니다.

- 내보내기가 안 여는 세트 60건 전체의 버전을 3으로 올렸다. 바뀐 칸은 그 세 칸뿐이고 원문은 그대로다.
- 연습 묶음(`dev.jsonl`)은 2판 그대로다. 같은 기준으로 갈리는 연습 문서 한 건(dev-023 운영 시간, 사람 확인 전)은 그대로 뒀다. 사람이 그 문서를 확인할 때 정한다.
- 옛 2판 파일은 저장소 밖에 `test.v2.jsonl` 로 남겨 두었다. `test.sha256` 은 3판 파일의 해시다.
- 확인 기록(`reviews.jsonl`)은 63줄이다: 연습 20줄, 안 여는 세트 40줄(측정 전에 사람이 남긴 것, 모두 맞음), 그리고 이 고침 3줄(고친 칸 1씩, 걸린 초는 비어 있다). 고친 세 건도 그 40줄에서는 "맞음"이었다(걸린 초 15 · 7 · 8초).
- 왜 고쳤고 무엇을 그대로 두었는지, 다시 채점한 값은 `docs/EVALUATION.md` 의 "정답을 고친 기록"과 `docs/EVAL-LOG.md` 의 "정답 3판 — 다시 채점"에 있다.

```bash
npm run gold:gen                 # 씨앗을 고정해 정답 100건의 설계도와 원문 쓰기용 묶음, 안내 글, 칸별 꼴 분포표를 만든다
npm run gold:gen -- assemble     # 써 온 원문과 정답을 합쳐 dev.jsonl, 저장소 밖 test.jsonl, test.sha256 을 쓴다
npx tsx scripts/gold-check.ts check      # 조립된 100건을 기계로 검산한다(조각이 원문에 있는가, 되읽은 값이 정답과 같은가, 없는 칸·정답에 없는 값이 샜는가)
npx tsx scripts/gold-check.ts selftest   # 원문을 일부러 망가뜨려 검산이 얼마나 잡는지 본다
npx tsx scripts/gold-check.ts measure    # 칸별 가장 흔한 표기 뼈대의 몫, 닮은 글 짝, 글 길이를 앞 판과 견준다
LABEL_ENABLED=1 npm run dev      # /label 에서 사람이 원문과 정답을 나란히 보고 확인한다(로컬 전용)
npm run gold:export              # 확인하며 고친 정답과 확인 기록을 파일로 되돌려 쓴다(고친 것이 있으면 정답 버전이 오른다)
npm run gold:load                # 파일의 정답을 DB 에 싣는다(--target test, --sealed, --real)
```

- 원문을 쓰는 동안의 작업 폴더(정답 설계도, 원문 묶음)는 저장소 밖에 둔다(`GOLD_WORK_DIR`, 없으면 홈 아래 `chaeum-gold-work`). 안 여는 세트의 정답이 들어 있어서다. 이번 차례의 파일은 그 안의 `v2/` 에 있고, 써 온 원문은 `v2/out/batch-N.json` 에 놓는다(조립기가 읽는 자리).
- 값 표기: 칸마다 원문에 적는 꼴을 여러 가지 두고(`src/gold/forms.ts`) 씨앗을 고정해 고르게 퍼뜨린다(`src/gold/assign.ts`). 한 꼴이 그 칸 문서의 30% 를 넘지 않는다. 정답 값은 표기와 따로 정해지므로 표기를 바꿔도 그대로다(시험이 해시로 본다). 꼴마다 정답 도구의 검산(`src/gold/recalc.ts`)이 되읽는지 시험한다.
- 연습 세트의 한계: 2판에서 표기가 갈렸어도 꼴은 생성기가 아는 것뿐이다. 처음 보는 표기에 대한 힘은 얼린 뒤의 실제 자료·손글 묶음에서 잰다.
- 한 줄이 한 건이다. 꼴은 `src/contract/eval-types.ts` 의 `GoldDocSchema`.
- 안 여는 세트를 저장소 밖에 두는 것은 약속이다. 잠금장치는 아니다. 정답 값은 씨앗으로 다시 만들 수 있고, 원문만 다시 만들 수 없다.
- `SEALED_GOLD_PATH` 는 절대 경로나 `~` 로 시작하는 길만 받는다. 상대 경로이거나 저장소 안을 가리키면 도구와 화면이 멈춘다(`src/gold/paths.ts`). 실제 자료의 원문이 저장소 안에 쓰이는 것을 막으려는 것이다. 그래도 생겼을 때를 대비해 `.gitignore` 가 `test.jsonl`, `real.jsonl`, `real-intake.jsonl` 을 이름으로 막는다.
- 이름(매체사, 업체, 그룹)은 전부 지어낸 것이다. 역과 동네 이름만 실제 지명이다.

## 사람 확인이 본 것

확인 화면은 칸을 고르면 생성기가 그 칸에 쓰라고 정한 표기를 원문에서 강조해 보여 준다(2026-10-12 저녁부터, 연습 묶음 9건을 확인한 뒤에 넣었다). 그래서 사람 확인은 "강조된 표기가 정답 값과 맞는가"와 "없음인 칸의 정보가 원문에 정말 없는가"를 본 것이다. 강조 밖의 글에 다른 값이 숨어 있는지는 기계 검산에 기댔다. 확인할 문서는 묶음마다 종류와 글 꼴이 고르게 섞이도록 씨앗으로 고른 일부다(연습 20 / 안 여는 세트 40). 확인하지 않은 문서는 채점에서 빠진다.

- 강조할 표기는 저장소 밖의 정답 설계도에서 읽는다(`LABEL_HINTS_PATH`, 없으면 작업 폴더의 `v2/specs.json`). 파일이 없으면 강조 없이 돈다.
- 칸 아래의 "환산 한 줄"(예: "월 3,000,000 ÷ 30 = 100,000")은 화면이 값을 새로 셈한 것이 아니다. 정답에서 거꾸로 셈한 수가 표기에 글자로 있을 때만 적고, 맞아떨어지지 않으면 아무것도 적지 않는다(`src/gold/explain.ts`).
- 확인할 문서를 고르는 법은 `src/gold/target.ts` 에 있다. 건수는 `LABEL_TARGET_DEV`, `LABEL_TARGET_TEST` 로 바꾼다. 이미 확인한 문서(버림 아님)는 반드시 들어간다.
- "하루 뒤 다시 보기"의 줄과 남은 시간 어림은 연습과 안 여는 세트의 기록만 쓴다(`src/gold/store.ts` 의 `CHECKED_SPLITS`). 실제 자료·손글을 저장해도 같은 씨앗은 같은 문서를 고른다.
- 잘못 누름을 줄이는 장치: 버림은 두 번 눌러야 되고, 바로 앞 문서의 판정은 되돌릴 수 있고(그 확인 기록 한 줄이 지워진다), 연 지 5초가 안 된 문서(등록 대상이 아닌 글은 3초)의 "확인 끝"은 한 번 되묻는다. 걸린 초는 되물은 시간까지 그대로 기록된다.

## 얼린 뒤에 만드는 두 묶음

파이프라인을 얼린 뒤에 사람이 만든다. 둘 다 로컬 전용 화면이다(`LABEL_ENABLED=1`). 넣은 글의 표는 이행 `0006` 이 만든다(`npm run db:migrate`).

### 실제 자료(real) — `/label/real`

1. 공개된 소개 글·단가표에서 상품 한 건에 해당하는 글을 붙여 넣고 출처 주소, 받은 날짜, 원문의 꼴을 적는다. 그림·PDF 는 사람이 글로 옮겨 붙인다.
2. 얼린 파이프라인(지금 쓰는 프롬프트 판, 가장 작은 모델, 코드의 맞추기·따지기)이 초안을 채운다. 실제 호출 1번이다. 같은 글은 다시 부르지 않는다. 초안은 한 번에 하나만 채운다(겹쳐 누르면 뒤의 것은 거절된다). 호출 수는 앱의 하루 상한과 따로 세고 화면 맨 위에 보인다(`LABEL_REAL_CALL_CAP`, 기본 60). 상한이 세는 것은 "답을 받아 초안이 된 호출 + 서버가 뜬 뒤 답을 못 받은 호출"이다. 서버를 다시 띄우면 못 받은 호출의 셈은 0 으로 돌아간다. 화면 맨 위의 수는 초안이 된 호출만이다.
3. 사람이 칸마다 "맞음 / 고침 / 없음으로 / 값 넣기"로 정답을 확정한다. 원문에서 강조되는 구절은 **모델이 준 근거 구절**이다(정답 설계도가 없는 묶음이라 달리 강조할 것이 없다).
4. 확정하면 정답 문서(`real-NNN`)가 DB 와 저장소 밖의 `real.jsonl` 에 생기고, 확인 기록이 한 줄 남는다. `npm run gold:export` 가 `real-sources.json`, `real-edits.json`, 저장소 밖의 `real-intake.jsonl` 을 쓴다.

**이 묶음의 숫자를 읽는 법.** 이 묶음의 정답은 "모델이 채운 것을 사람이 고쳐서" 만든다. 사람이 놓친 틀림은 맞은 것으로 세어진다. 그래서 이 묶음의 정확도는 모델에 유리하게 기운다. 이 묶음에서 내세우는 숫자는 정확도가 아니라 사람이 얼마나 손댔는가다.

- 모델이 채운 칸 가운데 사람이 고친 칸 ○/○ (분모는 모델이 값을 낸 칸 = 그대로 둔 칸 + 고친 칸 + 지운 칸)
- 사람이 새로 넣은 칸 ○ (모델이 놓친 값)
- 사람이 지운 칸 ○ (모델이 지어낸 값)
- 고친 것이 하나도 없는 문서 ○/○ (종류·갈래·칸 가운데 바꾼 것이 없는 문서)

셈은 `src/gold/origins.ts` 에 있다. "모델이 낸 값"은 넣은 글의 표(`gold_real_intake.model`)에, "사람이 확정한 값"은 정답 표(`gold_docs.truth`)에 따로 남고, "사람이 바꿨는가"는 둘을 견줘 낸다. 그래서 정답을 나중에 확인 화면에서 다시 고쳐도 셈이 지금 정답을 따른다.

- 모델이 낸 값은 초안에 실린 값이다(코드가 맞춘 값, 없으면 모델이 읽은 값. 평가의 `llm_code` 방식과 같다).
- 같다·다르다는 글자 그대로 견준다. 평가의 일치 기준(`docs/EVAL-SPEC.md`)보다 엄하다(예: 이름의 띄어쓰기만 고쳐도 "고침"이다).
- 빈 목록과 빈 글은 값이 아니라 "없음"이다. 모델 쪽과 사람 쪽에 같은 규칙을 쓴다. 모델이 빈 목록을 냈고 사람이 그대로 두면 "없음 그대로"이고 분모에 들지 않는다.
- 사람이 종류를 바꾸면 새 종류에도 있는 칸(이름, 판매가, 정가, 부가세)은 값을 견줘 "그대로"나 "고침"으로 센다. 새 종류에 없는 칸만 "지움"으로, 새 종류에 넣은 값은 "넣음"으로 센다.
- 그래서 "사람이 지운 칸"에는 두 가지가 섞인다: 모델이 지어낸 값, 그리고 종류를 바꿔서 빠진 칸. 종류를 바꾼 문서 수는 `real-edits.json` 의 `typeChanged` 로 따로 보인다.
- 확인 기록의 "고친 수"와 화면 알림의 "사람이 바꾼 것 ○개"는 바꾼 칸 수에 종류나 갈래를 바꿨으면 1을 더한 것이다(종류를 바꿔 갈래가 따라 바뀐 것은 한 번만 센다). 위의 네 숫자와는 다른 셈이다.
- 원문은 앱의 접수와 같은 정리(전각 → 반각, 이어진 공백 하나로)를 거친 꼴로 저장한다. 얼린 파이프라인이 읽는 것이 그 꼴이다. 4,000자까지다(앱의 접수 상한).
- 상품이 아닌 글(공지, 인사말)은 종류를 "등록 대상 아님"으로 바꿔 정답으로 저장한다. 우리 양식(광고 지면·케이터링·굿즈)에 없는 상품은 "넘김"으로 표시하고 정답 문서를 만들지 않는다. 넘긴 건도 출처 목록에 남는다(무엇을 골라냈는지 보이게).
- 너무 빨리 넘긴 건을 막지는 않는다. `a`(남은 칸 모두 맞음) → Enter → Enter 로 몇 초 만에 확정할 수 있다. 되묻기는 한 번뿐이다. 이 묶음은 사람이 놓치면 모델에 유리해지므로, `real-edits.json` 에 문서마다 확정할 때 본 초(`seconds`)를 함께 싣는다. 결과를 적을 때 이 초도 같이 보인다.
- 초안을 만든 호출의 답은 DB 의 장부(`llm_calls`)에 있고, `gold:export` 가 저장소 밖의 `real-intake.jsonl` 에도 쓴다. DB 를 새로 만들었으면 `npm run gold:load -- --real` 이 그 답을 장부에 다시 심는다. 심지 않고 평가를 돌리면 그 글을 다시 부르고, 사람이 본 초안과 다른 답을 채점할 수 있다(이 모델은 돌릴 때마다 조금씩 흔들린다).
- 넣은 글의 표가 아직 없으면(이행 `0006` 전) 화면과 API 가 오류 대신 `npm run db:migrate` 를 돌리라고 알린다.
- 평가기는 이 묶음을 안 여는 세트처럼 다룬다: `npm run eval -- --split real --i-know-this-opens-the-sealed-set --sealed <폴더>`. 결과 파일에는 원문에서 온 값을 싣지 않는다.

### 손글(hand) — `/label/hand`

사람이 원문을 직접 쓰고 정답 칸도 직접 채운다. 이 화면은 모델을 부르지 않고 모델의 답을 보여 주지 않는다. 이 묶음은 모델과 무관하게 만든 정답이다.

- 종류를 고르면 그 종류의 칸만 나온다. 칸마다 값의 꼴 안내가 있고, 적은 글을 어떻게 읽었는지 바로 보인다(예: `05:00~25:00` → 05:00 ~ 01:00, 끝이 다음 날). 읽는 법은 `src/gold/entry.ts`.
- 화면은 값을 새로 셈하지 않는다. 월 유동인구를 하루로 나누거나 mm 를 m 로 바꾸는 셈은 쓰는 사람이 한다(다른 단위를 적으면 되묻는다).
- 함정 귀띔(단위 없는 금액, 월 유동인구, mm 크기, 값이 없는 칸, 지시문 섞기 등)은 고르는 것이지 꼭 넣는 것이 아니다. 고른 것은 문서의 함정 꼬리표로 남는다.
- 원문과 정답이 모두 저장소에 들어간다. `npm run gold:export` 가 `hand.jsonl` 로 쓴다. 그 파일을 커밋한 시각이 "얼린 뒤에 썼다"의 증거다.
- 저장하면 확인 기록이 한 줄 저절로 남는다(새로 쓴 것은 `ok`, 고쳐 쓴 것은 `fixed` 와 정답에서 바뀐 칸 수). **이 기록은 쓴 사람이 저장하며 남긴 것이다. 다른 눈으로 다시 본 것이 아니다.** 평가기가 확인 기록이 있는 문서만 채점하기 때문에 남긴다.
- 평가: `npm run eval -- --split hand`. 저장소 안의 파일이라 긴 깃발 없이 돈다(긴 깃발은 저장소 밖에 두는 두 묶음에만 있다).
