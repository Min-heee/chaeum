# 평가 결과

- 기준은 `docs/EVAL-SPEC.md`에 먼저 적어 두었다. 이 문서는 그 기준으로 잰 값을 싣는다.
- **지금 상태(2026-10-13): 안 여는 세트(`test`)의 지표 여섯을 냈다. 지금 싣는 값은 정답 3판으로 다시 채점한 것이다.** 얼린 파이프라인(꼬리표 `freeze-v1`)으로 사람이 정답을 확인한 40건을 세 번 불렀다(그때 정답은 2판). 그 뒤 사람이 기준 하나를 정했고("배달 도착 시간은 운영 시간이 아니다") 정답 세 칸이 "없음"으로 바뀌어 3판이 됐다. 그래서 그때 받아 둔 같은 답을 새 정답으로 다시 채점했다. 다시 부른 것이 아니다(실제 호출 0건). 3판 값은 아래 "안 여는 세트" 절에, 2판 때의 값은 그 절 끝의 "정답 2판 때의 값"에, 고친 까닭은 "정답을 고친 기록"에 있다. 주입 시험(모델 호출 0번)도 실려 있다.
  - 안 여는 세트 60건 가운데 사람 확인 기록이 있는 문서는 40건이다. 남은 20건은 재지 않았다. 연습 세트는 40건 가운데 20건이다.
  - 실제 자료 세트(`real`) 20건과 손글 세트(`hand`) 10건은 아직 없다. 두 묶음의 지표는 아직 내지 못했다.
  - 녹화 재채점의 기준 파일(`eval/baseline.json`)은 연습 묶음의 것이다. 사람이 확인한 연습 20건에서 "전부 맞은 문서 수"가 기준 아래로 내려가는지만 지킨다. 안 여는 세트로는 기준을 만들지 않는다.
  - `eval/results/`의 연습 3건 실행 기록은 정답 1판 때의 것이고 확인 전 문서가 들어 있다. 지금 정답은 연습 묶음 2판, 안 여는 세트 3판이다. 지우지 않고 그대로 둔다.

- 모든 비율 옆에 분자/분모를 적는다. 분모가 0이면 "해당 없음(0건)"이라고 쓴다.

## 돌리는 법

```bash
npm run eval -- --split dev --dry-run          # 대상 건수, 장부에 있는 건수, 어림 비용. 키가 없어도 된다
npm run eval -- --split dev --limit 3          # 3건만
npm run eval -- --split dev --max-usd 0.3      # 넘을 것 같으면 멈추고 끝난 데까지 저장
npm run eval -- --split dev --prompts v1,current   # 프롬프트 판을 건별로 견주기
npm run eval -- --split dev --prompts v2 --fresh  # 장부를 읽지도 쓰지도 않고 모두 다시 부른다(같은 판을 두 번 재 볼 때. 돈이 든다)
npm run eval -- --split dev --prompts v2 --fresh --keep-answers  # 위와 같되 받은 답을 실행별 파일(data/recordings/runs)에 따로 남긴다
npm run eval:inject                            # 주입 시험. 모델 호출 0번
npm run eval:replay                            # 녹화본으로 연습 세트 다시 채점. npm run verify 의 마지막 단계
npx tsx --env-file-if-exists=.env.local eval/compare.ts <앞 실행 번호> <뒤 실행 번호>   # 두 실행의 건별 나아짐·나빠짐
```

- 기본으로 도는 것은 연습 세트뿐이다. 안 여는 묶음(`test`, `real`)은 `--i-know-this-opens-the-sealed-set` 과 `--sealed <경로>` 를 함께 줘야 열리고, 돌릴 때마다 `eval_runs`에 남는다.
- 사람이 확인하지 않은 문서는 채점에서 빠진다. 뺀 건수가 함께 찍힌다. `--include-unreviewed` 로 넣으면 실행 기록에 "확인 전 포함"이 남는다.
- 한 번 돌리면 문서마다 뽑기를 한 번 부르고, 그 한 번에서 세 방식(`rules` / `llm_only` / `llm_code`)을 채점한다. `eval_runs` 3줄과 `eval_results`, 그리고 `eval/results/` 의 기록(JSON)과 요약(틀린 건 목록 포함)이 남는다.
- 이미 받은 답은 장부에서 읽는다. 같은 문서를 다시 돌려도 돈이 들지 않는다. `--fresh`를 주면 장부를 읽지도 쓰지도 않고 모두 다시 부른다. 거기에 `--keep-answers`를 더하면 받은 답을 `data/recordings/runs/` 아래 실행별 파일(기록 파일과 같은 머리 이름)에 남긴다. 장부가 아니라서 다음 실행과 회귀 문지기는 이 답을 읽지 않는다. 원문 표현과 읽은 값을 나중에 들여다볼 때 쓴다. `--keep-answers`는 연습 세트에서만 답을 남긴다. 다른 묶음의 답은 남기지 않는다.
- 프롬프트 판 이름: `current`는 앱이 쓰는 판이다(지금 `extract-v1`). `v2`, `v3`, `v4`, `v5`는 연습 세트에서 재 보고 버린 판이라 견줄 때만 쓴다. 판마다 장부의 키가 달라 답이 섞이지 않는다.
- 답을 못 받은 문서는 빼지 않는다. LLM 두 방식에서 빈 답으로 채점하고 몇 건인지 적는다.

  - 측정 뒤 AI가 틀린 칸이 있는 문서 14건을 다시 읽어 다시 볼 칸을 냈다. 사람이 그 가운데 두 문서를 다시 보고 기준을 정했다. 그 뒤 AI 둘이 운영 시간에 값이 있는 정답 9건을 훑었고, AI 도구가 세 칸을 고쳤다.
  - 세 건 모두 측정 전 확인에서는 사람이 "맞음"으로 넘긴 문서다(확인 기록의 걸린 초 15 · 7 · 8초).
  - 그 가운데 두 칸(test-024·test-033)은 2판에서 세 번 모두 "맞음"으로 채점되던 칸이다. 이 세트는 정답을 먼저 정하고 원문을 나중에 쓴다(`data/gold/README.md`). 만든 차례로 미루어 보면, 원문을 쓴 AI가 운영 시간 값을 배달·도착 시간대로 풀어 썼고, 읽는 AI는 그 시간을 운영 시간 칸에 적어 정답과 맞았다. 사람 확인은 강조된 표기가 값과 같은지를 본 것이라 이것을 잡지 못했다. 아래 단서 1(쓴 AI와 읽는 AI가 같은 회사 모델)과 이어지는 일이다.
  - 맞았다고 채점된 나머지 칸의 정답은 따로 검증하지 않았다. 그런 칸이 더 있어도 이 측정으로는 드러나지 않는다.

## 안 여는 세트 — 모델 claude-haiku-5-5, 프롬프트 extract-v1, 정답 v3, 커밋 671f0f9-dirty(코드는 `freeze-v1`과 같다)

이 절의 값은 최종 측정 때 받은 답(세 번)을 정답 3판으로 다시 채점한 것이다(실행 76~84, 실제 호출 0건). 답은 같고 정답 세 칸이 달라졌다. 정답 2판 때의 값은 이 절 끝의 "정답 2판 때의 값"에 남겼다. 두 판의 실행을 나아짐·나빠짐으로 견주지 않는다(`docs/EVAL-SPEC.md` 8절).

**먼저 읽을 단서 여섯**

1. 합성 자료다. 원문은 AI가 썼고, 읽는 AI도 같은 회사의 모델이다. 글 꼴과 표기가 읽는 쪽에 유리할 수 있다. 실제 공급처 글에서의 정확도가 아니다.
2. 정답을 확인한 사람이 한 명이다(40건, 건당 평균 28초, 측정 전 확인에서는 고친 칸 0). 두 사람의 일치도는 없다.
3. 60건 가운데 종류와 글 꼴이 고르게 섞이도록 고른 40건이다. 무작위 표본이 아니고, 남은 20건은 재지 않았다.
4. 같은 프롬프트도 부를 때마다 답이 달라진다. 그래서 세 번을 모두 적는다. 가장 좋은 한 번을 고르지 않는다. 같은 40건을 세 번 부른 것이라 세 번을 합쳐도 문서를 뽑는 데서 오는 오차는 줄지 않는다.
5. 40건이라 비율의 오차 폭이 넓다(아래 대략의 95% 구간). 한두 건이 2.5~5%p를 움직인다.
6. 지금 정답(3판)은 측정 결과를 본 뒤에 세 칸을 고친 것이다. 기준은 사람이 정했고, 세 칸 가운데 한 칸(test-033)은 AI가 같은 꼴로 찾았고, 적용은 AI 도구가 했다. 세 건 모두 측정 전에는 사람이 "맞음"으로 넘긴 문서다. 고친 세 칸이 모두 점수를 내리는 쪽은 아니다. test-019는 둘째·셋째에서 놓침이 맞음이 됐다(세 칸을 합친 결과가 이 절의 값이다). 다시 볼 것으로 나온 다른 칸은 그대로 두었다. 그 가운데 하나(test-051 부가세 포함)는 바꾸면 점수가 오르는 쪽이다.

### 방식 셋 비교 (같은 문서, 같은 호출)

"규칙만"은 기준선으로 대충 짠 것이다. 규칙만과 LLM의 차이를 개선이라고 부르지 않는다. 기준선을 대충 짤수록 커지는 숫자다. 규칙만은 호출이 없어 세 번이 똑같다.

- `llm_only`와 `llm_code`는 같은 호출의 답을 두 가지로 채점한 것이다.
- 지어낸 값은 세 방식 모두 0이 아니다. `llm_only`와 `llm_code`는 같은 칸이다(test-024·test-033 운영 시간 세 번, test-019 운영 시간 첫째). 규칙만이 지어낸 3칸은 test-019·test-033 운영 시간(규칙도 글의 배달 시간대를 운영 시간으로 집었다)과 test-053 해상도다.

### 틀린 칸 (`llm_code`)

세 번을 합쳐 서로 다른 틀린 줄(문서 × 칸, 갈래 줄 포함)은 23줄이다. 세 번 모두 틀린 것 7줄, 두 번 4줄, 한 번만 12줄. 번마다는 15줄(칸 12 + 갈래 3) / 11줄(칸 10 + 갈래 1) / 15줄(칸 11 + 갈래 4)이다.
갈래는 AI가 원문을 읽고 나눈 것이다(2판 때 틀린 칸이 있던 문서 14건, 그리고 정답을 훑을 때 본 test-033). 사람이 다시 본 것은 test-019·test-024 두 문서이고, 사람이 정한 것은 운영 시간 세 줄에 쓰인 기준 하나다. test-033에 그 기준을 댄 것은 AI다. 띄어쓰기나 괄호처럼 채점이 엄해서만 틀린 칸은 없다.

### 고치기 전 코드와 얼린 코드 (같은 답으로)

연습 묶음을 보고 고친 두 가지(시도 1 선언된 금액 단위, 시도 6 감싼 꼴 벗기기)가 처음 보는 40건에서 무엇을 했는지 본 것이다. 고치기 전 코드(커밋 edee1dd, 프롬프트는 같은 extract-v1)를 저장소 밖에 꺼내 같은 답 40건으로 다시 채점했다(실제 호출 0건). 아래는 정답 3판으로 다시 센 값이다. 두 코드를 같은 정답 3판으로 채점한 것이라 나아짐·나빠짐으로 견줄 수 있다. 저장소 밖 스크립트로 아무것도 남기지 않고 센 것이라 `eval_runs`와 `eval/results`에 남은 기록은 없다. 같은 스크립트를 얼린 코드에 돌리면 위 표와 한 줄도 다르지 않은 판정이 나온다.

### 연습 묶음과 나란히

**연습 묶음의 숫자는 고칠 때 본 묶음의 것이다. 내세우는 숫자가 아니고, 안 여는 세트가 얼마나 낮은지 보려고만 나란히 놓는다.** 연습 쪽은 같은 얼린 코드·같은 프롬프트로 세 번 본 것이다(실행 51 · 54 · 57, `docs/EVAL-LOG.md` 시도 7). 연습 묶음의 정답은 2판 그대로다.

| `llm_code` | 연습 20건 (고칠 때 본 묶음, 정답 2판) | 안 여는 세트 40건 (정답 3판) |
|---|---|---|
| 칸 정확도 | 210/212 · 210/212 · 207/212 | 396/405 · 397/405 · 396/405 |
| 틀린 칸 | 2 · 2 · 5칸 | 12 · 10 · 11칸(값이 있는 칸에서 9 · 8 · 9, 지어낸 칸 3 · 2 · 2) |
| 전부 맞은 문서 | 17/20 · 17/20 · 14/20 | 29/40 · 32/40 · 30/40 |
| 표시 없이 틀린 칸 | 0 · 0 · 0 | 4 · 4 · 3 |
| 바로 승인 줄 안의 틀린 문서 | 0/5 · 0/6 · 0/5 | 2/11 · 1/11 · 2/11 |
| 지어낸 값 | 0/52 세 번 | 3/83 · 2/83 · 2/83 |

- 안 여는 세트가 낮다. 연습의 좋은 두 번보다 칸으로 1.0~1.3%p(99.1% 대 97.8~98.0%), 문서로 5~12.5%p(85% 대 72.5~80%) 낮고, 연습의 나쁜 한 번(207/212, 14/20)과는 비슷하거나 조금 높다.
- **연습 묶음에 맞춘 티가 조금 있다고 읽는 것이 정직하다.** 연습에서 고친 두 가지는 여기서 문서 1 · 1 · 3건만 도왔고, 같은 갈래의 틀림(선언이 아래에 있는 표, 목록에 없는 이름표, 붙여 쓴 맺는 말)이 새로 나왔다. 표시 없이 틀린 칸, 승인 줄 안의 틀린 문서, 지어낸 값은 연습에서는 한 번도 없었고 여기서 처음 나왔다.

| 묶음 | 방식 | 앞 판 → 뒤 판 | 문서: 나아짐 / 나빠짐 / 그대로 | 칸: 나아짐 / 나빠짐 |
|---|---|---|---|---|
| 안 여는 세트 | — | 견줄 판이 없다 | — | — |

- 얼린 판이 첫 판(`extract-v1`) 그대로다. 연습 묶음에서 재 본 `extract-v2`~`extract-v5`는 모두 버렸다. 그래서 `docs/EVAL-SPEC.md` 9절의 "첫 판 프롬프트와 마지막 판을 함께"는 한 판만 잰 것이 됐다.

## 주입 시험

검사기를 재는 것이다. 모델을 재는 것이 아니다. 씨앗: 20261012 (값 종류마다 최대 30곳)

2026-10-13에 다시 돌린 값이다(`npm run eval:inject`, 모델 호출 0번, 기록 `eval/results/inject.json`). 2026-10-12의 첫 값과 다른 곳은 아래 "망가뜨리기 전" 줄의 값 재료 수뿐이다(216칸 → 218칸, 표시가 붙은 칸 16칸 → 18칸. 까닭은 `docs/EVAL-LOG.md` 시도 1).
값 넷의 재료는 연습 세트 2판(사람 확인 전)의 원문이다. 재료가 바뀌면 넣은 수도 바뀐다.

| 종류 | 잡은 수 / 넣은 수 | 예상과 다른 사유로 잡힘 |
|---|---|---|
| 금액에 0 하나 더 `zero_added` | 22/22 | 0 |
| m ↔ mm 뒤바꿈 `unit_swap` | 17/17 | 0 |
| 원문에 없는 근거 `fake_evidence` | 30/30 | 0 |
| 기간이 길수록 싸지는 값 `cheaper_longer` | 5/5 | 0 |
| 혼잣말 넣기 `monologue` | 20/32 | 0 |
| 용어 바꾸기 `glossary_swap` | 32/32 | 0 |
| 자리표시 지우기 `placeholder_removed` | 16/16 | 0 |
| 한글 섞기 `hangul_mixed` | 32/32 | 0 |

- 망가뜨리기 전의 헛경보(값 재료 / 글 재료): 값 재료 218칸(문서 31건) 가운데 원래부터 표시가 붙은 칸 18칸(망가뜨릴 곳에서 뺐다) / 글 재료 32줄 가운데 원래부터 걸린 글 0줄
- 못 잡은 종류와 그 까닭: 혼잣말 12곳. 모두 글 **뒤에** 붙인 문장이다("(Note: placeholder kept as requested.)" 6곳, "如需修改请告诉我。" 4곳, "（注：已保留占位符）" 2곳). 혼잣말 검사는 꼴 목록이고 글 끝의 덧말은 목록에 없다. 시험을 보고 그 문장만 목록에 더하는 것은 시험에 맞추는 일이라 하지 않았다.
- 다 잡은 일곱 종류도 "넣은 곳을 다 잡았다"까지만 말한다. 넣은 수가 5~32곳이라 못 잡는 경우가 없다는 뜻이 아니다.

주입 시험이 재는 것과 재지 못하는 것
- 값 넷의 재료는 "규칙으로 찾은 표현을 코드가 맞춘 값이 정답과 일치하는 칸"이다. 규칙이 못 찾는 칸은 재료에 없다.
- 망가뜨리기 전부터 표시가 붙던 칸은 망가뜨릴 곳에서 뺀다(넣으면 저절로 잡힌 것으로 세어진다).
- `cheaper_longer`는 원문도 그렇게 적혀 있는 것으로 하고 범위 검사만 본다. 모델 값만 바꾸면 값 불일치로 먼저 잡힌다.
- 글 넷의 재료는 직접 지은 제목·요약이다. 모델이 쓴 글이 아니다.

## 한계

- 안 여는 세트 절 맨 위의 단서 여섯. 실제 자료와 손글 묶음의 지표는 아직 내지 못했다.
- **지어낸 값이 0이 아니다(3/83 · 2/83 · 2/83).** 정답 2판에서는 0/80으로 세어졌다. 모델의 답은 같다. 사람이 "배달 도착 시간은 운영 시간이 아니다"라고 정해 세 칸의 정답이 "없음"이 되면서 드러난 것이다(세 칸 가운데 한 칸은 AI가 같은 꼴로 찾았다). 그 가운데 두 칸(test-024·test-033)은 2판에서 세 번 모두 "맞음"으로 세던 칸이다.
- 표시 없이 틀린 칸이 0이 아니다(4 · 4 · 3칸. 틀린 칸 12 · 10 · 11칸 가운데). 바로 승인 줄 안의 틀린 문서는 2/11 · 1/11 · 2/11이다. 뿌리는 셋이다.
  - 모델이 배달·도착 시간을 운영 시간 칸에 적는다. 글에 적힌 시간을 옮긴 값이라 어느 검사에도 걸리지 않는다. 검사기는 근거가 원문에 있는지, 코드가 읽은 값과 모델이 읽은 값이 같은지, 값이 범위 안인지를 볼 뿐이고, 그 시간이 무엇의 시간인지는 보지 않는다. 승인 줄 안의 틀린 문서 5건(세 번 합)이 모두 이 꼴이다.
  - 모델이 선택 칸을 아예 안 내면 검사기가 볼 것이 없다(test-051 부가세 포함).
  - 이름의 일부만 읽은 값은 원문에 그대로 있어 어느 검사에도 안 걸린다(test-003 상품 이름).
- 갈래만 틀리고 목록 안의 다른 갈래를 낸 문서에는 사유가 안 붙는다. 그런 문서가 바로 승인 줄에 설 수 있고, 5번 지표에는 갈래가 들지 않아 숫자에 보이지 않는다.
- 선언된 금액 단위는 선언이 값보다 아래에 있으면 못 따른다(10배 틀림, 표시는 붙는다). 감싼 꼴 벗기기는 목록에 없는 이름표와 값에 바로 붙은 맺는 말을 못 벗긴다(표시는 붙는다).
- 지금 정답(3판)은 측정 결과를 본 뒤에 세 칸을 고친 것이다. 고친 것, 그대로 두기로 한 것, 아직 안 본 것은 아래 "정답을 고친 기록"에 있다. 훑은 것은 운영 시간에 값이 있는 정답 9건뿐이다. 맞았다고 채점된 다른 칸의 정답은 여전히 검증하지 않았다.
- 둘째·셋째 측정의 답은 저장소 밖에만 있다. 이 저장소만으로 다시 채점할 수 있는 것은 장부에 답이 있는 첫째뿐이다(그것도 평가를 돌린 개발 DB가 있어야 한다). 정답 3판 다시 채점의 둘째·셋째도 그 저장소 밖 답 파일로 했다.
- 모델 하나(claude-haiku-5-5), 프롬프트 한 판, 한 날의 측정이다.
- 본보기의 보기 글 12건에서 눈으로 본 놓친 예 둘(값으로 센 것이 아니다):
  - "중국어 섞인 문의" 글은 원문에 지면 이름이 있는데 상품 이름을 뽑지 못했다. 필수 칸 빔 표시가 붙어 사람이 본다.
  - "여러 정보가 뒤섞인 긴 글"은 "도착 시간 11시~13시"를 운영 시간으로 읽었고, 표시 없이 "바로 승인 가능"으로 갔다. 표시 0개인데 틀린 건의 실제 예다. 이 문장은 정답 2판 때부터 있었다. 그때 안 여는 세트의 정답은 같은 꼴(배달·도착 시간대)을 운영 시간으로 적고 있어 이 문장과 어긋났다. 정답 3판에서 사람이 정한 기준과 같은 방향이 됐고, 안 여는 세트에서도 같은 꼴이 도시락 문서 셋(test-019·024·033)에서 나왔다.
- 구조 규칙 가운데 셋(필수 옵션 0개, 종류와 갈래 불일치, 자리 채움 글자)은 보기 글에서 한 번도 뜨지 않는다. 단위 시험과 칸 고치기 시험으로만 확인했다.

## 정답을 고친 기록

평가 뒤 정답이 틀린 것으로 드러나면 정답 버전을 올리고, 몇 건을 왜 고쳤는지 적은 뒤 다시 채점한다. 옛 버전의 결과는 지우지 않는다(`docs/EVAL-SPEC.md` 9절).

### 정답 3판 (2026-10-13, 최종 측정 뒤) — 안 여는 세트 3건, 3칸

| 문서 · 칸 | 2판 정답 | 3판 정답 | 글에 적힌 것 |
|---|---|---|---|
| test-019 운영 시간 `service_hours` | 08:00~11:00 | 없음 | "도착은 08:00~11:00 사이" |
| test-024 운영 시간 `service_hours` | 09:00~12:00 | 없음 | "배달 나가는 시간대" |
| test-033 운영 시간 `service_hours` | 09:00~11:00 | 없음 | "Delivery time … 09~11시" |

- 왜 고쳤나: 사람이 기준을 정했다. "배달 도착 시간은 운영 시간이 아니다. 도착 시간이다." 세 건 모두 도시락 상품이고, 글에 적힌 시간은 배달이 나가거나 도착하는 시간대다.
- 누가 정하고 누가 적용했나:
  - 기준은 사람(정답을 확인한 사람)이 정했다. 최종 측정 뒤 AI가 낸 "다시 볼 것" 목록을 받고, 확인 화면에서 test-019와 test-024를 다시 본 뒤다.
  - 같은 꼴이 더 있는지는 AI 둘이 따로 훑었다. 정답 세트 전체에서 운영 시간에 값이 있는 문서 9건(연습 3, 안 여는 세트 6)을 보았고 둘의 가름이 같았다: 분명한 배달·도착 시간 3건(test-019, test-024, test-033), 분명한 운영 시간 5건(모두 커피차: dev-009, dev-027, test-003, test-004, test-049), 갈리는 것 1건(dev-023). test-033은 사람이 짚은 문서가 아니라 이 훑기에서 AI가 찾은 것이다. 사람이 test-033의 글을 다시 봤다는 기록은 없다. 그 글이 기준에 드는지는 AI 둘의 가름이고, 사람은 적용을 맡겼다.
  - 적용은 사람이 맡겨서 AI 도구가 했다. 확인 화면과 같은 저장 함수를 썼다. **사람이 손으로 누른 것이 아니다.** 확인 기록의 "고침" 3줄(고친 칸 1씩)은 걸린 초가 비어 있고, 그것이 도구가 적용했다는 표시다.
- 정답 버전과 해시: 안 여는 세트만 2판 → 3판이다. 내보내기가 묶음 전체 60건의 버전을 3으로 올렸다. 바뀐 칸은 위의 세 칸뿐이고 원문은 그대로다. 연습 묶음은 2판 그대로다. 옛 2판 파일은 저장소 밖에 `test.v2.jsonl`로 남겼다(해시 `bd20b4d9d7ce…`). 새 해시는 `data/gold/test.sha256`에 있다(`0f1815aa3682…`). 고치기 전 정답 세 건은 저장소 밖 기록 폴더에도 따로 남겼다.
- 다시 채점: 최종 측정 때 받아 둔 같은 답을 새 정답으로 다시 채점했다(실행 76~84, 실제 호출 0건, $0). 옛 2판 실행(67~75)과 기록 파일은 그대로 있다. 숫자가 어떻게 달라졌는지는 위 "정답 2판 때의 값"의 끝과 `docs/EVAL-LOG.md`의 "정답 3판 — 다시 채점"에 있다.
- 읽을 때의 단서: 결과를 본 뒤에 고친 정답이다. 이번에 고친 세 칸 때문에 `llm_code`의 지어낸 값은 0/80 세 번에서 3/83 · 2/83 · 2/83으로, 승인 줄 안의 틀린 문서는 0/11 · 1/11 · 1/11에서 2/11 · 1/11 · 2/11로 세어진다. 고친 세 칸이 모두 점수를 내리는 쪽은 아니다. test-019(사람이 직접 다시 본 문서다)는 둘째·셋째에서 놓침이 맞음이 됐다. 그 두 번에서는 이 칸이 표시 없이 틀린 칸에서 빠지고, 문서가 승인 줄 안의 틀린 문서에서 전부 맞은 문서로 옮겨 간다. 세 칸을 합친 값이 앞 문장의 값이다. 바꾸면 점수가 오르기만 하는 칸(test-051 부가세 포함)은 고치지 않았다.
- 다른 문서와 어긋나는 곳(그 문서들은 고치지 않고 여기에 적어 둔다): `docs/PRD.md` 7절은 합성 묶음의 정답을 코드가 먼저 정한다고 적는다(정답이 모델에서 나오지 않게 하려는 것). 이 세 칸의 3판 정답은 그 길로 정해진 값이 아니다. 사람이 정한 기준으로 "없음"이 됐고, 한 칸(test-033)은 AI의 가름이다. 같은 절의 "정답이 틀렸으면 버전을 올리고 몇 건을 왜 고쳤는지 적는다"는 따랐다. 기준 "배달 도착 시간은 운영 시간이 아니다"는 이 문서와 `docs/EVAL-LOG.md`, `data/gold/README.md`에만 있다. 칸 정의의 귀띔(`src/contract/fields.ts`, 얼린 곳이라 그대로다)과 `docs/EVAL-SPEC.md`, `docs/PRD.md`·`docs/DECISIONS.md`의 이력에는 아직 없다.
