# 고른 것과 고르지 않은 것

- 상태(2026-10-12): 파이프라인·API·화면·평가기를 합치고 검토에서 나온 결함을 고친 뒤다. 공개 배포는 아직 하지 않았다. 정답 세트의 사람 확인도 끝나지 않았다. 잰 값이 나오면 고치고, 고친 날짜를 적는다.
- 아직 재지 않은 것은 "미확인"이라고 적는다. 잰 숫자는 5절 이력에, 몇 번 잰 것인지와 함께 적는다.

## 1. 고른 것

| 무엇 | 고른 것 | 이유 | 버린 것과 이유 |
|---|---|---|---|
| 언어 | TypeScript (Node.js 22 이상) | 화면, API, 판단 코드, 평가기가 같은 타입을 쓴다. 칸 정의 하나에서 검증 스키마와 타입이 함께 나온다 | 다른 언어로 서버를 따로 두기: 약속 파일을 두 벌로 써야 한다 |
| 틀 | Next.js(App Router) 하나에 화면과 API | 주소 하나, 배포 하나. 경로 파일은 얇게 두고 판단은 `src/core`, DB와 작업 줄은 `src/server`에 둔다. 그래서 서버를 떼어 내기 쉽다 | 서버를 따로 띄우기: 무료 호스팅이 하나 더 필요하고 잠든다. 큰 서버 틀: 이 크기에 무겁다 |
| DB | PostgreSQL 16, `pg`로 SQL을 직접 쓴다 | 중복 접수, 동시 승인, 작업 집기가 모두 DB의 제약과 잠금으로 풀린다. SQL이 눈에 보여야 설명할 수 있다 | SQLite: 여러 요청이 같은 줄을 잠그는 일을 보여 주지 못한다 |
| 이행 | 번호 붙은 `.sql` 파일 + 적용 기록 표 하나 | 무엇이 언제 바뀌었는지 파일 이름으로 보인다. 두 번 돌려도 안전하다 | 이행 도구: 파일 하나를 적용하는 데 도구가 필요하지 않다 |
| 작업 줄 | PostgreSQL 표 하나 + `FOR UPDATE SKIP LOCKED` + 임대 시각 + 재시도 + `dead` | 부품이 하나 준다. 접수와 작업 넣기가 한 트랜잭션에 들어간다. 하루 수백 건 규모다. 실무라면 pg-boss 같은 검증된 도구부터 본다. 여기서는 원리를 설명할 수 있게 직접 짧게 쓴다 | Redis와 별도 대기열: 서비스가 하나 더 필요하고 고장 날 곳이 는다 |
| 검증 | zod | API 입력, LLM 출력, 정답 파일을 같은 방식으로 본다 | — |
| LLM | Anthropic API. 공급자 자리 하나에 구현 셋(실제 호출 / 녹화 재생 / 시험용) | 키 없이도 시험과 공개 시연이 돈다. "바꿔 끼울 수 있다"의 증거는 이 자리에 셋이 실제로 끼워져 돈다는 것이다 | LLM 틀(체인류): 한 번 부르는 일에 층이 두껍다. 다른 회사 모델: 재 보지 못한 코드는 넣지 않는다 |
| 구조화 출력 | SDK의 스키마 지정 출력 + 서버에서 zod로 다시 검사 | 숫자 범위 같은 제약은 API가 강제하지 않는다. 받은 뒤 다시 본다 | 도구를 강제로 고르게 하는 방식: 새 모델에서 오류가 난다(구현할 때 다시 확인) |
| 모델 | 기본은 가장 작은 모델. 이름은 환경 변수 | 건당 비용이 작다. 충분한지는 연습 세트에서 재 보고 정한다(미확인) | 처음부터 큰 모델: 예산을 넘는다 |
| 시험 | vitest. 단위 시험과 DB 시험을 가른다. DB 시험은 진짜 PostgreSQL | 잠금과 동시성은 진짜 DB에서만 확인된다. LLM은 시험용 구현으로 바꾼다 | DB 흉내: 통과해도 믿을 수 없다 |
| 배포 | 무료 호스팅 + 무료 PostgreSQL | 가입 없이 주소 하나로 열린다. 아직 올리지 않았다. 한도(함수 시간, 잠든 DB가 깨는 시간, 연결 수)는 미확인이다. 올려서 잰 뒤 이 문서의 이력에 적는다 | — |

## 2. 구조에서 정한 것

**LLM은 값 찾기 한 번만 맡고, 단위 맞추기와 검사는 코드가 한다.**
글에서 값을 찾는 일은 꼴이 끝없이 달라 규칙으로 따라가기 어렵다. 단위·범위·숫자 넣기는 틀리면 돈이 걸리고, 코드는 같은 입력에 늘 같은 답을 낸다.

**한 번의 호출에서 원문 표현과 읽은 값을 함께 받는다.**
"LLM만"(읽은 값 그대로)과 "LLM + 코드"(원문 표현을 코드가 맞춤)를 같은 호출로 견줄 수 있다. 둘이 다르면 그것이 검수 신호(`VALUE_MISMATCH`)다. 호출 수는 늘지 않는다.

**확신 점수를 모델에게 묻지 않는다.**
신호 셋(근거가 원문에 있나, 코드가 읽은 값과 같은가, 규칙을 통과하나)으로 만들고, 점수 대신 사유 코드를 남긴다. 사유는 사람이 읽을 수 있고 따로 잴 수 있다.

**초안은 느슨하게, 확정 상품은 엄격하게.**
초안은 칸 하나가 한 줄이라 칸 단위로 고치고 채점하고 집계한다. 승인되면 타입과 CHECK가 있는 `products`로 옮긴다. 제약은 코드 검사가 놓친 것을 막는 마지막 줄이다. 종류별 규격과 옵션은 jsonb로 두고 넣기 전에 코드가 꼴을 본다. 표를 종류별로 가르지 않은 것은 설명할 수 있는 만큼만 만들기 위해서다.

**호출 장부가 곧 캐시이자 녹화본이다.**
키 = sha256(일 + 모델 + 프롬프트 버전 + 스키마 버전 + 시스템 글의 해시 + 모델에 보내는 스키마의 해시 + 생각 깊이 + 정리한 입력). 그림·PDF가 붙은 요청은 입력에 파일의 종류·형식·해시가 함께 들어간다. 버전 이름을 그대로 두고 프롬프트 글이나 칸 정의만 고쳐도 키가 달라져 옛 답이 섞이지 않는다. 최대 토큰 수는 키에 넣지 않았다. 시험용 구현이 장부에 적은 줄은 녹화로 치지 않는다.

**글 만들기 요청에 숫자를 넣지 않는다.**
모델은 `{price}` 같은 자리표시만 쓰고 숫자는 코드가 넣는다. 번역 글의 숫자가 원래 값과 달라질 길이 없다. 값을 고쳐 승인해도 같은 요청이라 녹화 응답이 그대로 맞는다.

**시각과 난수는 인자로 받는다.**
판단 코드와 작업 줄은 지금 시각을 직접 읽지 않는다. 시험에서 시계를 돌려 임대 만료와 재시도를 확인한다. 린트 규칙이 `Date.now`, `Math.random`, 인자 없는 `new Date()`를 막는다.

**LLM을 부르는 동안 DB 트랜잭션을 열어 두지 않는다.**
집기(짧게) → 호출 → 저장(짧게). 처리기는 여러 번 돌아도 결과가 한 번만 남게 쓴다.

**요청이 작업을 굴린다(공개 시연).**
공개 시연에는 계속 도는 작업자가 없다. 접수 직후와 화면이 상태를 물을 때 줄을 굴리는 API를 부른다. 요청이 끝난 뒤에 뒤에서 도는 기능은 쓰지 않는다. 화면이 부르는 쪽이 설명하기 쉽다. 따로 도는 작업자는 로컬에서만 쓴다.

**작업 공간은 첫 쓰기 때 만든다.**
주소를 여는 것만으로는 아무것도 만들지 않는다. 봇이나 링크 미리보기로 DB가 차지 않는다.

**일치 기준을 구현보다 먼저 커밋한다.**
결과를 본 뒤 기준을 고르면 숫자를 믿을 수 없다. `docs/EVAL-SPEC.md`가 평가기와 파이프라인보다 앞선 커밋에 있다.

## 2.1 v0.2에서 정한 것 (2026-10-12)

**방문자가 직접 넣은 글에 실제 호출을 연다.**
- 왜: 보기 글만 AI 답이 나오고 자기 글은 "규칙만"으로 가면, 이 도구가 하는 일을 방문자가 자기 글로 확인할 길이 없다. "녹화한 답만 보여 주는 사이트"와 구분되지 않는다.
- 길을 고르는 순서(한 건마다, `src/contract/pipeline-api.ts`의 `planLlmRoute`): 장부에 그 요청의 답이 있으면 그것을 쓴다 → 없고 실제 호출이 열려 있으면 부른다 → 아니면 "규칙만" 길로 가고 사유 `LLM_SKIPPED`와 원인을 남긴다.
- 원인은 일곱 가지다(`drafts.llm_skip_cause`): 키 없음 / 녹화 없음 / 꺼져 있음 / 글이 김 / 오늘 상한이 참 / 모델이 거절 / 호출 실패. 화면이 "왜 AI를 거치지 않았는지"를 이 말로 적는다. 요청에 적힌 여섯에 "글이 김"을 하나 더했다. 길어서 안 부른 것을 "꺼져 있음"이나 "실패"로 적으면 틀린 말이 되기 때문이다.
- 막는 장치는 다섯 겹이다.
  1. 하루 전체 건수 상한(`LIVE_LLM_DAILY_CAP`). 기본값 0 = 꺼짐. 호출하기 **전에** `daily_counters`를 올리고, 실패해도 돌려놓지 않는다. 호출 하나가 한 건이다(글로 옮기기·뽑기·글 만들기가 따로 세고, 다시 한 시도도 센다). 환경 변수에 큰 수를 잘못 적어도 1,000에서 자른다.
  2. 글이 2,000자를 넘으면 부르지 않는다. 파일은 3MB, PDF는 10쪽까지다.
  3. 가장 작은 모델, 답의 최대 토큰 수를 단계별로 묶는다.
  4. 모델에게 도구가 없고 답은 스키마에 묶인 JSON 하나다. 결과는 방문자 자기 공간에만 쓰인다.
  5. 키 자체에 지출 한도를 건다(콘솔에서). 코드가 틀려도 여기서 멈춘다.
- 잠깐의 오류(429·5xx·시간 초과)는 작업 줄이 다시 한다. 세 번째에도 안 되면 초안을 실패로 두지 않고 "규칙만" 결과를 낸다(원인: 호출 실패). 방문자가 빈손으로 끝나지 않게 하려는 것이다.
- 한계: 상한은 "하루 전체"다. 한 사람이 다 써 버리면 그날 다른 방문자는 "규칙만" 길로 간다. 방문자별 상한은 로그인이 없어 두지 않았다. 하루 몇 건으로 둘지는 실제 건당 비용을 잰 뒤 정한다(미확인).

**그림·PDF는 따로 글자 인식 엔진 없이 모델에 그대로 넘긴다.**
- 왜: 단가표는 표·도장·손글씨·기울어진 사진이 섞여 온다. 글자 인식 엔진을 따로 두면 설치물이 하나 늘고, 엔진이 틀린 것과 모델이 틀린 것을 따로 재야 한다. 모델이 그림을 직접 읽으면 부품이 늘지 않고 호출이 한 번 는다.
- 두 번 부른다: 먼저 "보이는 그대로 옮겨 적기"(`transcribe`), 그 글로 "칸 뽑기"(`extract`). 한 번에 뽑지 않는 까닭은 따지기가 **원문 글**을 필요로 하기 때문이다(근거 구절이 원문에 있는가). 옮긴 글이 그 원문이 되고, 붙여 넣은 글과 같은 길을 탄다.
- 글로 옮기기는 작업 줄에 넣지 않고 올리기 요청 안에서 끝낸다. 파일을 저장하지 않기로 했으므로 줄에 넣어 둘 것이 없다. 남는 것은 옮긴 글, 파일의 해시, 파일 이름뿐이다. 같은 공간에 같은 파일을 다시 올리면 모델을 부르지 않고 기존 건을 돌려준다.
- 장부 키에 파일의 해시가 들어간다. 안 넣으면 다른 그림이 같은 키가 되어 남의 답이 나온다(시험이 지켜본다). 파일 자체는 장부에도 넣지 않는다.
- 브라우저가 보낸 형식 이름은 믿지 않고 파일 머리 바이트로 형식을 정한다.
- 한계:
  - **옮기다 틀린 것은 코드가 잡지 못한다.** 근거 검사는 "옮긴 글" 안에서 근거를 찾으므로, 모델이 "150"을 "180"으로 옮겼으면 근거도 "180"으로 있다. 그래서 이런 초안에는 막는 사유 `TRANSCRIBED`("원본과 대조 필요")가 늘 붙고, 바로 승인 줄에 들어가지 않는다. 파일을 저장하지 않으므로 화면에 원본을 나란히 보여 주지도 못한다. 사람이 가진 원본과 대조해야 한다.
  - 그림은 규칙만 길이 없다. 모델을 못 부르면 접수하지 않고 까닭을 돌려준다.
  - 글로 옮기기는 지어낸 단가표 한 장으로 그림 1번·PDF 1번 불러 본 것이 전부다(있어야 할 구절 15개가 둘 다 그대로 나왔다). 정답 세트로는 재지 않았다. 정답 세트는 전부 글이다.
  - 암호가 걸린 PDF 는 호출 전에 막는다. 한 변이 8,000px 을 넘는 그림과 세로로 아주 긴 그림은 막지 않는다(모델 쪽이 거절하거나 줄여서 읽는다).
  - 모델이 옮기며 적은 덧말("2주 값이 가려져 있다" 같은 말)은 버린다. 화면에 보일 자리가 약속에 없다.
  - PDF 쪽수는 파일 안의 표식을 세는 어림이다. 표식이 눌려 있는 PDF는 쪽수를 모르고 통과한다. 진짜 상한은 파일 크기와 하루 호출 상한이다.
  - 옮긴 글이 4,000자를 넘으면 받지 않는다. 긴 소개서는 쪽을 나눠 올려야 한다.

**양식 맞춤 파일은 "열 목록" 하나다.**
`{name, columns: [{header, from 또는 value, format?}]}`. 칸 이름과 순서, 고정값, 몇 가지 서식(가로만·세로만·쉼표·Y/N)까지만 한다. 조건문이나 계산식은 넣지 않았다. 필요해지면 그때 코드로 쓴다.

**번역 검사 API는 모델을 부르지 않는다.**
이미 번역된 글을 받아 글 검사 5종만 돌려준다. 어느 숫자가 맞는 숫자인지는 부르는 쪽이 알려 줘야 하고, 안 주면 숫자 검사는 "건너뜀"으로 답한다(통과로 적지 않는다).

## 2.2 딸린 도구에서 정한 것 (2026-10-12)

결정 문서는 `docs/PRD-TOOLS.md`, 약속은 `src/contract/tools/`에 도구별 파일로 있다. 이 절을 쓸 때는 약속·이행·메뉴·빈 화면까지만 있었다. 도구 여섯의 구현은 그 뒤다.

**도구는 본체가 채운 칸을 읽기만 한다.**
견적의 총액은 기간·수량 옵션에서, 시안 검사의 규격은 해상도·파일 형식·한 번 길이 칸에서, 달력의 마감은 예약·소재 마감 일수 칸에서 그대로 읽는다. 도구가 값을 다시 뽑거나 따로 저장하지 않는다. 점검도 새 규칙을 만들지 않고 본체의 구조 규칙과 글 검사를 전 상품에 돌린다(사유 코드도 본체의 것이다).

**날짜 세기는 한 군데(`src/tools/shared/deadline.ts`)에 둔다.**
견적과 달력이 같은 함수로 마감을 센다. 마감일 = 기준일 − 일수, 남은 날 = 마감일 − 오늘. 마감 당일은 "곧 마감"이고 아직 된다. 남은 날 3일까지를 "곧 마감"으로 본 것은 근거 없이 정한 값이다(약속의 `DEADLINE_RULES`). 날짜는 시각 없는 달력 날짜로만 다루고 오늘은 인자로 받는다.

**견적에서 모델은 읽기만 하고, 돈과 날짜는 코드가 센다.**
조건 뽑기에서 모델은 날짜를 "5월, 첫 주" 같은 조각으로만 낸다. 그것을 올해인지 내년인지 정하고 날짜 범위로 바꾸는 것은 코드다. 예산은 적힌 표현을 본체의 금액 맞추기가 다시 읽고, 못 읽을 때만 모델이 읽은 값을 쓰며 그렇게 표시한다. 답장은 숫자와 날짜를 자리표시로만 쓴다. 조건 뽑기에는 대신할 규칙 길이 없어, 모델을 못 부르면 접수하지 않는다(그림 올리기와 같다). 실제 호출은 본체와 같은 하루 상한을 함께 쓴다.

**용어 사전은 공간별이고, 본보기 공간의 줄이 공용 줄이다.**
- 왜: 로그인이 없다. 표 하나를 모두가 고치게 두면 한 방문자가 다른 방문자의 번역 표기를 바꿀 수 있다. 본체의 칸막이(작업 공간)를 그대로 썼다. 공용 줄은 씨앗만 쓰고 방문자는 읽기만 한다. 방문자가 같은 낱말을 자기 공간에서 승인하면 그 공간에서만 그 표기가 이긴다.
- 글 만들기·글 검사·번역 검사는 승인된 줄만 본다(`src/server/repos/glossary-terms.ts`의 `approvedGlossary`, 고르는 규칙은 약속의 `effectiveGlossary`).
- 장부 키: 요청에는 그 상품에 해당하는 줄의 세 칸(한국어·영어·중국어)만 한국어 낱말 순서로 들어간다. 번호·상태·메모는 들어가지 않는다. 그래서 씨앗 파일에서 표로 옮겨도, 상관없는 낱말을 더해도 키가 그대로다(시험이 본다).
- 공용 줄이 한 줄도 없는 DB(이행만 하고 씨앗을 안 심었다)에서는 씨앗 파일을 그대로 쓴다. 시험 DB 와 처음 받은 저장소에서 글 만들기가 전과 같게 돌게 하려는 것이다.
- 줄을 지우는 길은 두지 않았다. 승인을 풀면 쓰이지 않는다.

**시안 검사는 큰 파일을 서버로 보내지 않는 길을 함께 둔다.**
호스팅이 받는 요청 본문이 4.5MB 까지라 영상 시안은 대개 올리지 못한다. 파일 머리를 읽는 함수를 바이트만 받는 순수 함수로 두면 브라우저에서도 돈다. 그래서 화면이 읽은 값만 보내는 길을 약속에 넣었다. 그 길에서는 서버가 파일을 보지 못했다는 것을 응답(`readBy: 'client'`)과 화면이 적는다.

**모으기: 줄을 초안으로 만들 때 모델을 부르지 않는다.**
정리된 줄의 값을 "원문 표현"으로 삼아 본체의 맞추기·따지기를 그대로 거친다. 뽑은 방식과 원문 종류에 `import`를 더했다. 중복은 서버가 정한다. 열쇠는 "위치·호선·역·매체 종류·가로·세로"를 이은 글자이고(해시를 쓰지 않아 눈으로 볼 수 있다), 수집기와 서버가 같은 식을 쓰도록 `docs/IMPORT-FORMAT.md`에 보기 줄과 함께 적었다. 이름은 위치가 모두 비었을 때만 열쇠에 넣는다. 그래서 다른 출처가 같은 자리를 다른 이름으로 적어도 한 건이 되지만, 한 자리에 같은 규격의 매체가 둘이면 하나로 합쳐진다(알고 둔 약점).

**XLSX 는 `write-excel-file`로 쓰고 `read-excel-file`로 읽는다.**
- 고른 이유: 같은 사람이 관리하는 작은 패키지 둘이고 2026년에도 판이 나온다. 쓰는 쪽의 의존은 압축 패키지 하나다. 시트 여러 장과 수·글자 칸 구분이면 충분하다.
- 버린 것: `exceljs`는 읽기와 쓰기가 한 패키지지만 마지막 판이 2023년이고 설치물이 20MB 를 넘으며 낡은 압축 패키지들에 기댄다. `xlsx`(SheetJS)는 npm 에 올라 있는 판이 오래됐고 알려진 취약점이 고쳐지지 않은 채다.
- 읽는 쪽은 점검이 XLSX 파일을 받을 때 쓴다. 남이 올린 압축 파일을 푸는 일이라 파일 크기(1MB)와 줄 수(500)를 먼저 묶는다.
- 시트는 셋이다: "상품"(한 줄에 상품 하나), "옵션"(한 줄에 기간·수량 옵션 하나, 상품번호로 잇는다), "안내". 글자 칸은 글자 타입으로 쓰므로 CSV 처럼 수식 막기 따옴표를 붙이지 않는다.

**본보기 공간에는 씨앗이 승인해 둔 상품 일곱이 있다.**
- 왜: 견적·시안 검사·달력·점검은 승인된 상품을 읽는다. 본보기 공간에 상품이 없으면 처음 온 사람에게 넷 다 빈 화면이다.
- 어떻게: 씨앗이 보기 글 열둘 가운데 일곱의 초안을 운영자 자리에서 승인한다(변경 기록에 `admin`의 승인으로 남는다). 글은 받아 둔 답으로 붙인다. 검수 API 는 본보기 공간에 쓰지 못하므로 씨앗이 저장 함수를 직접 부른다. 두 번 돌려도 같다.
- 남긴 것: 지시문이 섞인 글, 값이 빠진 글 둘, 등록 대상이 아닌 글 둘은 검수함에 그대로 있다. 사람이 판단할 것을 씨앗이 대신 승인하지 않는다.
- 값: 승인한 일곱 가운데 셋은 "확인 필요"였다(단위 바꿈 표시 등). 씨앗은 값을 고치지 않고 그대로 승인한다. 그래서 합정역 전광판은 "하루 유동인구"가 빈 채로 상품이 됐고, 점검이 그것을 잡는다.

**견적은 본보기 공간의 상품을 읽어 계산할 수 있다(`catalog: 'public'`).**
새 방문자의 공간에는 상품이 없어 견적이 늘 "맞는 상품 0개"였다. 요청에 살필 상품의 자리를 더했다. 본보기 상품은 누구나 읽을 수 있는 것이고, 견적은 여전히 요청한 공간에 저장한다(본보기 공간에는 쓰지 않는다). 견적 표에 열 하나(이행 0005)가 생겼다. 보기 문의 20건의 답장은 본보기 상품의 이름으로 다시 받아 두어, 키 없는 서버에서도 끝까지 뜬다.

**본보기 공간에 공공 자료 30줄을 싣는다.**
수집기는 공개 사이트에서 돌지 않는다. 모으기 화면이 무엇을 다루는지 보이게, 출처 표시를 조건으로 다시 쓸 수 있는 자료(공공누리 1유형) 하나에서 30줄만 저장소에 두고 씨앗이 싣는다. 업체 이름 칸은 뺐다. 출처는 화면의 묶음 표와 `docs/COLLECTOR.md`에 적었다. 나머지 출처의 줄은 업소 이름이 들어 있어 넣지 않았다.

**딸린 도구의 판단 코드는 `src/tools/`에 두고 본체의 린트 규칙을 그대로 건다.**
시계·난수·DB·네트워크를 쓰지 못한다. 파이썬 수집기는 저장소 맨 위 `collector/`에 따로 두고, 타입 검사·린트·시험·빌드가 그 폴더를 보지 않게 했다.

## 3. 넣지 않은 부품

| 부품 | 넣지 않은 이유 | 대신 |
|---|---|---|
| ORM | 작업 줄과 조건부 UPDATE의 SQL이 가려진다 | `pg`로 직접 쓴 SQL |
| Redis, 별도 대기열 서버 | 서비스가 하나 더 필요하다. 이 규모에 필요 없다 | `jobs` 표 하나 |
| 멱등 키 표 | 같은 글은 (작업 공간, 내용 해시) 유일 제약으로, 같은 작업은 (종류, 대상 번호) 유일 제약으로 막는다 | 유일 제약 둘 |
| 수정 금지 트리거 | 변경 기록에 "추가만 한다"는 코드와 시험으로 지킨다. 트리거는 설명할 것이 하나 더 는다 | 코드 + 시험 |
| 임대 표식 열(누가 집었는지) | 임대 시각 하나로 회수할 수 있다. 끝내기는 "집을 때 받은 시도 횟수와 임대 시각"이 그대로일 때만 먹는다. 결과는 초안이 처리 중일 때만 쓰므로 두 번 처리해도 한 번만 남는다 | `leased_until` |
| 고침 기록 표 | 변경 기록의 `edit` 줄이 곧 "사람이 고친 값"이다 | `draft_events` |
| 토큰 표, 로그인, 권한 | 등록 전 단계만 다룬다. 방문자는 작업 공간 번호로만 나뉜다 | 요청 헤더의 공간 번호 |
| 종류별 상품 표 | 표 하나에 핵심 열만 제약을 건다. 나머지는 jsonb | `products.spec` |
| 에이전트, 도구 호출 | 한 번 부르고 한 번 받는 일이다. 모델에게 도구를 주지 않으므로 원문 속 지시문이 할 수 있는 일도 없다 | 스키마에 묶인 답 하나 |
| 벡터 DB, 검색 | 찾아올 문서가 없다. 원문 한 건이 통째로 들어간다 | — |
| 웹 수집 | 직접 만든 가상 페이지를 직접 읽는 것은 수집이라 할 수 없다. 실제 판매 사이트는 어떤 형태로도 긁지 않는다. 예외는 하나다: 공공기관이 내려받으라고 올려 둔 파일을 출처 목록대로 받는 수집기(`collector/`) | 붙여 넣기 접수, 공공 자료 파일 |
| 주소 → 좌표 | 바깥 유료 API가 필요하다 | — |
| 글자 인식(OCR) 엔진 | 그림·PDF는 모델에 그대로 넘겨 글로 옮긴다(2.1절). 엔진을 하나 더 두면 설치물과 재야 할 것이 는다 | 모델 호출 한 번 |
| 올린 파일 보관(파일 저장소) | 파일을 남기지 않는다. 옮긴 글과 파일의 해시만 남긴다. 저장소 서비스와 지우는 규칙이 필요 없어진다 | `source_docs`의 열 셋 |
| 결제, 주문, 정산 | 등록 전 단계만 다룬다 | — |
| UI 라이브러리 | 화면이 몇 장뿐이다 | 전역 CSS 한 장 |
| 딸린 도구마다 따로 서버 | 한 앱의 꼭지로 둔다. 모으기의 받기·정리만 파이썬 폴더다 | `app/<도구>`, `app/api/<도구>` |
| 달력 라이브러리, 날짜 라이브러리 | 날짜 더하기·빼기 넷이면 된다. 시간대가 끼어들지 않게 달력 날짜만 다룬다 | `src/tools/shared/deadline.ts` |
| 영상·그림 해석 도구(ffprobe 등) | 가로·세로·길이는 파일 머리 몇 바이트에 있다. 설치물을 늘리지 않는다 | 머리 바이트를 읽는 순수 함수 |
| 메신저·알림 연결 | 견적의 "보내기"는 표에 확정으로 적는 것까지다 | `quotes.status` |
| 용어 줄 지우기 | 승인을 풀면 쓰이지 않는다. 지우는 길과 그 권한을 따로 설명하지 않아도 된다 | `status = 'proposed'` |
| CI | 로컬에서 `npm run verify`가 통과하는 것이 먼저다. 여유가 되면 넣는다 | `npm run verify` |

## 4. 알고 있는 약점

- 직접 쓴 작업 줄은 검증된 도구보다 다뤄 본 경우가 적다. 시험이 확인하는 것은 넷이다: 같은 글 두 번, 동시 승인, 표에 없는 상태 이동, 임대가 끝난 작업의 회수.
- 방문자를 나누는 것은 추측하기 어려운 번호 하나뿐이다. 비밀 자료를 담는 구조가 아니다.
- "안 여는 세트"는 약속이지 잠금장치가 아니다. 진짜 장치는 파이프라인을 얼린 뒤에 모으는 실제 자료 세트와 손글 세트다. 사람이 확인 화면을 열면 안 여는 세트가 개발 DB(`gold_docs`)에도 실린다. 고치는 동안에는 그 묶음의 줄을 조회하지 않는다. 이것도 약속이다.
- 하루 접수 세기(`daily_counters`) 줄은 접수 트랜잭션이 끝날 때까지 잠긴다. 공간이 달라도 접수는 이 줄에서 한 줄로 선다(50건 묶음이 도는 동안 다른 접수가 기다린다). 되돌리면 세기도 함께 되돌아가는 쪽을 골랐다. 하루 수백 건 규모에서는 문제 삼지 않는다. 잠금·멈춘 트랜잭션의 시간 제한(`lock_timeout` 등)은 걸지 않았다. 배포할 DB 의 연결 방식을 확인한 뒤 정한다.
- 번호만 받는 저장 함수(`listFields`, `saveFields`, `listEvents`, `getDraftById`, `getProductById`, 글 읽고 쓰기)는 공간을 보지 않는다. 지금은 공간으로 먼저 거르는 함수 뒤에서만 부른다. 경로 파일을 붙일 때 이 순서를 지켜야 한다.
- 규칙만으로 뽑는 길은 숫자 칸보다 글자 칸(이름, 지역, 재질)이 약하다. 문장 꼬리가 값에 붙거나, 이름표 없는 글에서 이름을 못 찾는다. 종류 낱말이 없는 글("옥외 비전", "미디어월"만 적힌 광고)은 등록 대상 아님으로 낸다.
- 맞추기가 일부러 읽지 않는 표기가 있다(읽으면 조용히 틀리기 쉬워서): 부가세 낱말이 없는 "별도·포함", "15초 또는 30초", 시간당·주 단위 횟수, "1억5천", 범위 열쇠가 든 값표("1~2주"), 낱개 값이 섞인 값표("1잔당"), 오전·오후 없는 "1시~5시", "불가"가 섞인 형식 목록. 이런 칸에는 `PARSE_FAILED`가 붙고 사람이 본다.
- 단위 없는 작은 금액("5,000", "3500")은 만원이 빠진 것으로 읽고 `UNIT_CONVERTED`를 붙인다. 굿즈의 "5,000"은 5천원일 가능성이 높아 이 짐작이 틀린다. 사유가 붙어 사람이 보지만 값 자체는 틀릴 수 있다.
- 글 검사는 글자로 쓴 수("two weeks", "一百五十万")를 숫자로 잡지 못한다. 용어는 부분 일치라 낱말 속에 묻혀 있어도 통과한다. 짧은 덧말("Translated from Korean")도 혼잣말 꼴 목록에 없으면 지나간다.
- 지시문 찾기는 꼴 목록이다. 목록에 없는 말투의 지시는 지나간다. 막는 장치는 "원문을 값으로만 넘긴다"와 "모델에게 도구가 없다"이고, 이 검사는 사람에게 알리는 표시일 뿐이다.
- `npm run verify`의 마지막 단계(녹화 재채점)는 기준 파일(`eval/baseline.json`)이 없으면 "기준 없음"이라고 찍고 통과한다. 기준은 사람이 확인한 연습 세트를 한 번 다 돌린 뒤에 만든다. 그 전에는 이 단계가 아무것도 지키지 않는다.
- 글 검사는 글 **뒤에** 붙는 혼잣말을 놓친다. 주입 시험(씨앗 20261012, 한 번 돌림, 기록 `eval/results/inject.json`, 표는 `docs/EVALUATION.md`)에서 혼잣말 32곳 가운데 20곳을 잡았고, 놓친 12곳은 모두 글 끝에 붙인 문장이었다("(Note: …)", "如需修改请告诉我。"). 시험을 보고 그 문장만 목록에 더하는 것은 시험에 맞추는 일이라 하지 않았다.
- 글자 칸(위치 등)은 코드가 원문 표현을 그대로 최종 값으로 싣는다. 모델이 더 깔끔하게 다듬은 값이 있어도 덮인다(표시는 붙는다). 연습 3건 가운데 1건에서 봤다. 흔한지는 전체를 돌려야 안다.
- 본보기 공간의 상품 일곱은 사람이 아니라 씨앗이 승인한 것이다(2.2절). 내려받기는 방문자가 자기 공간에서 승인한 상품만 된다. 값이 빠져 바로 상품이 될 수 없는 보기 글(둘)은 글 만들기 녹화본이 없어, 방문자가 칸을 채워 승인하면 실제 호출(상한 안) 또는 틀 문장이 된다.
- 견적의 지역 견주기는 글자의 포함 관계다. 본보기 상품으로 보기 문의 20건을 돌리면 절반이 "맞는 상품 없음"이다("홍대 근처"와 "합정역", "성수동"과 "서울 전 지역"이 맞지 않는다). 지도를 모른다는 한계가 시연에서 그대로 보인다. 표는 `docs/EVALUATION-TOOLS.md`.
- 모으기의 중복 열쇠에는 출처가 없다. 역도 주소도 없는 자료 둘이 같은 호선·같은 매체 이름을 적으면 도시가 달라도 한 줄이 된다(부산·대구 자료에서 실제로 2줄이 그랬다). 그 두 출처에는 지역을 적어 고쳤지만, 같은 꼴의 새 출처를 붙일 때마다 사람이 봐야 한다.
- 모은 줄은 공간 하나에 2,000줄까지다. 수원 자료(정리된 줄 115,147)는 한 공간에 들어가지 않는다. 큰 자료를 통째로 올려 두는 용도가 아니다.
- 화면을 지키는 자동 시험이 없다. 딸린 도구의 화면은 사람이(이번에는 AI 가 브라우저로) 열어 본 것이 전부다.
- 요청 횟수 제한은 없다. 줄 굴리기와 번역 검사는 누구나 부를 수 있다. 막는 것은 하루 상한과 건수·크기 상한뿐이다. 초안 하나에 쌓이는 변경 기록은 200줄에서 멈춘다(칸 고치기·다시 돌리기가 429). 공간당 초안 100건이므로 한 공간이 쌓을 수 있는 기록에도 끝이 있다. 다만 공간을 새로 만드는 횟수 자체는 하루 접수 상한(2,000건)까지 막지 않는다.
- PDF 쪽수는 PDF 를 다 읽어서 세는 것이 아니다. 쪽 표식을 세고(이름의 16진 표기는 풀어서), 눌린 객체 묶음은 풀어서 그 안도 센다. 그래도 세지 못한 PDF 는 받지 않는다. 작정하고 꾸민 파일(다른 방식으로 누른 묶음에 쪽을 숨기고 보이는 쪽을 하나만 둔 것)은 여전히 지나갈 수 있다. 그런 파일 하나의 호출 비용은 문서에 적은 건당 값보다 클 수 있다. 실제로 재지 않았다. 마지막 줄은 하루 호출 상한과 키의 지출 한도다. 부르기 전에 토큰 수를 먼저 세어 보는 길(무료 호출)은 넣지 않았다.
- 상품의 글이 미리 받아 둔 답인지 방금 받은 답인지는 글마다 남기지 않는다(초안의 뽑기에는 남긴다). 남기려면 글 표에 열이 하나 더 필요하다.
- 글 작업이 죽으면 틀 문장 넷이 "글 확인 필요"로 남는다. 화면에서 글 작업만 다시 줄 세우는 길은 없다.
- 본보기의 보기 글 둘은 놓친 예다("중국어 섞인 문의"는 이름을 못 뽑았고, "여러 정보가 뒤섞인 긴 글"은 도착 시간을 운영 시간으로 읽고도 표시가 없다). 숨기지 않고 `docs/EVALUATION.md`의 한계에 적었다.
- 용어집에 보기 글의 낱말 몇이 없다(키링, 스크린도어, 미디어보드). 용어집을 고치면 글 만들기 요청의 키가 바뀌어 녹화본을 다시 받아야 하므로, 다음에 녹화할 때 함께 고친다.
