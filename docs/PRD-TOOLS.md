# 채움 — 딸린 도구 PRD v0.1

- 날짜: 2026-10-12 · 상태: 일곱 개와 수집기를 만들었다(2026-10-13. 일곱째인 비교는 v0.2 에서 더했다). 잰 것은 [EVALUATION-TOOLS.md](EVALUATION-TOOLS.md), 수집기는 [COLLECTOR.md](COLLECTOR.md) · AI가 쓴 초안이고, "여섯 개를 다 만든다"는 것은 사람이 정했다.
- 본체(등록·검수·평가)의 결정 문서는 [PRD.md](PRD.md)다. 이 문서는 본체 옆에 붙는 도구 일곱 개만 다룬다.

## 1. 왜 붙이나

본체는 제각각인 글에서 값을 뽑아 **정리된 상품**으로 만든다. 딸린 도구는 두 가지를 보여 준다.

- 등록의 **앞**과 **옆**: 자료를 모아 오는 일(모으기), 이미 올라간 상품을 살피는 일(점검, 용어 사전).
- 값을 정리해 두면 **뒤에서 무엇이 되는가**: 총액 계산(견적), 규격 대조(시안 검사), 마감 거꾸로 세기(달력). 셋 다 본체가 채운 칸(값, 기간 옵션, 해상도, 파일 형식, 예약·소재 마감 일수)을 그대로 읽는다.

## 2. 지킬 순서

1. 본체가 먼저다. 딸린 도구가 본체의 평가(정답 확인, 개선, 최종 측정)를 밀어내지 않는다.
2. 만드는 순서는 아래 번호 순서다. 첫 공개 때 못 들어간 것은 README의 "아직 아닌 것"에 그대로 적는다.
3. 판단은 순수 함수와 시험으로, API는 얇게. 본체와 같은 규칙이다.
4. 가상 마켓과 지어낸 자료만 쓴다. 예외는 1번(모으기)의 공공 자료 하나다.

## 3. 도구 일곱

### 3-1. 점검 — 이미 올라간 상품 전체를 한 번에 살핀다

- **누가**: 운영자. 상품이 쌓인 뒤 "어디가 잘못 올라가 있나"를 본다.
- **입력**: 등록된 상품 전체, 또는 양식 꼴 CSV 파일.
- **하는 일**: 본체의 구조 규칙(필수 옵션 0개, 종류·갈래 불일치, 자리 채움 글자, 값 범위)과 글 검사(빈 번역, 한글 섞임, 혼잣말 흔적, 용어 표기, 숫자 어긋남)를 전 상품에 돌린다.
- **출력**: 사유별·심각도별 묶음, 상품별 문제 목록, CSV 내려받기.
- **LLM**: 쓰지 않는다.
- **끝났다는 기준**: 일부러 망가뜨린 상품 묶음에서 넣은 문제 수와 잡은 수를 종류별로 낸다.

### 3-2. 모으기 — 공공 자료를 받아 한 꼴로 정리한다 (파이썬)

- **누가**: 운영자. 여러 기관이 제각각 낸 전광판·옥외광고 현황 파일을 상품 초안의 재료로 쓴다.
- **입력**: 출처 목록(주소, 이용 조건, 받은 날짜). 수집이 허용된 공공 자료만 쓴다.
- **하는 일**: 파일 받기 → 글자 인코딩 판별 → 출처별 칸 대응표로 칸 이름 맞추기 → 꼴 정리 → 같은 위치·규격의 중복 제거 → 본체의 접수 API로 넘기기. 값 맞추기와 검사는 본체 서버가 다시 한다(한 곳에서만 판단한다).
- **출력**: 본체의 초안(뽑은 방식 = 가져오기). 가격 칸이 없는 자료이므로 "필수 칸 없음" 표시가 붙어 검수함으로 간다.
- **LLM**: (여유) 처음 보는 출처의 칸 이름을 우리 칸에 대응시키는 제안 1회. 사람이 승인한 대응표만 파일로 남긴다.
- **지킬 것**: robots.txt, 요청 간격, 출처별 이용 조건 기록. 원자료는 저장소에 넣지 않는다(받는 스크립트와 출처 목록만). 변경을 금지한 자료는 고친 판을 배포하지 않고 로컬에서만 쓴다.
- **끝났다는 기준**: 출처 수, 받은 줄 수, 초안이 된 줄 수, 중복으로 뺀 줄 수, 못 읽은 줄 수를 그대로 낸다. `pytest` 통과.
- **한계**: 실제 판매 상품이 아니라 설치 현황 자료다. 가격이 없다. 자기 사이트를 스스로 긁는 것이 아니라는 점까지만 말한다.

### 3-3. 용어 사전 — 번역 표기를 한곳에서 정한다

- **누가**: 운영자. "커피차"가 언어마다 같은 말로 옮겨지게 한다.
- **하는 일**: 용어 표(한국어 → 영어·중국어 간체 표기, 상태: 제안/승인). 글 검사는 승인된 용어만 본다.
- **LLM**: (여유) 상품 글에서 용어 후보를 제안. 승인은 사람만 한다.
- **한계**: 내가 읽지 못하는 표기는 승인하지 않는다.

### 3-4. 견적 — 문의 글에서 조건을 뽑아 맞는 상품과 총액을 낸다

- **누가**: 상담 담당. 해외 팬이 한·영·중으로 보낸 문의에 답한다.
- **입력**: 문의 글("예산 300만 원, 홍대 근처, 5월 첫 주 생일 광고").
- **하는 일**

| 단계 | 누가 | 하는 일 |
|---|---|---|
| 조건 뽑기 | LLM 1회 | 예산, 지역, 날짜, 종류, 수량. 없으면 "없음" |
| 고르기·계산 | 코드 | 조건에 맞는 상품, 기간·수량 옵션으로 총액, 오늘 기준 예약·소재 마감에 맞는지 |
| 답장 초안 | LLM 1회 | 문의한 언어로. 숫자는 자리표시로만 쓰고 코드가 넣는다 |
| 글 검사 | 코드 | 본체와 같은 검사 |
| 확인 | 사람 | 고쳐서 보냄(보내기는 흉내만) |

- **끝났다는 기준**: 조건 뽑기 정확도(칸별, 분자/분모), 고른 상품이 조건을 만족하는 비율(코드로 검증), 총액 계산은 시험으로 확인.
- **한계**: 메신저 연결이 없다. 돈 계산은 모델이 하지 않는다.

### 3-5. 시안 검사 — 광고 시안 파일이 지면 규격에 맞는지 본다

- **누가**: 팬(주문자)과 운영자. 규격이 안 맞아 다시 받는 왕복을 줄인다.
- **입력**: 지면 하나 + 시안 파일(JPG·PNG, MP4).
- **하는 일**: 파일 머리에서 가로·세로·형식·길이·용량을 읽어 그 지면의 규격과 견준다. 안 맞으면 무엇을 얼마로 고칠지 적는다.
- **LLM**: 쓰지 않는다. 파일은 저장하지 않는다.
- **끝났다는 기준**: 규격별로 맞는 파일과 일부러 틀리게 만든 파일을 시험으로 가른다.
- **한계**: 내용 심사(문구, 초상)는 하지 않는다.

### 3-6. 달력 — 기념일에 맞추려면 언제까지 무엇을 해야 하나

- **누가**: 팬과 상담 담당.
- **입력**: 기념일(가상 가수의 생일·데뷔일), 오늘 날짜(인자로 받는다).
- **하는 일**: 지면마다 예약 마감 일수와 소재 마감 일수를 거꾸로 세어 "아직 되는 지면 / 며칠 남음 / 이미 늦음"을 낸다.
- **LLM**: 쓰지 않는다.
- **끝났다는 기준**: 날짜 경계(마감 당일, 달이 바뀌는 날, 윤년)를 시험으로 확인.

### 3-7. 비교 — 정리된 상품을 같은 잣대로 나란히 놓는다

- **누가**: 운영자. 여러 공급처가 보낸 상품을 견주어 무엇을 올리고 무엇을 권할지 고른다.
- **왜 되나**: 공급처마다 값을 다르게 적는다("1주 150", "월 600만 원", "하루 21만 원"). 본체가 그것을 한 꼴로 정리해 두었기 때문에 같은 잣대로 나란히 놓을 수 있다.
- **입력**: 등록된 상품(승인된 것). 종류와 갈래, 지역으로 거른다.
- **하는 일**: 정리된 칸에서 견줄 수 있는 값을 계산한다. 하루당 값(기간 옵션에서), 하루 유동인구 1,000명당 값, 화면 넓이, 하루 운영 시간, 하루 송출 횟수, 예약·소재 마감. 표로 늘어놓고 칸마다 차례를 바꿔 볼 수 있다. 둘에서 넷까지 골라 나란히 놓으면 다른 칸이 눈에 띄게 보인다.
- **지키는 것**: 값이 없는 칸은 "없음"으로 둔다. 다른 칸에서 짐작해 채우지 않는다. 옵션에 없는 기간의 값을 나눠서 지어내지 않고, 어느 옵션에서 계산했는지 함께 적는다. 부가세 포함과 별도가 섞이면 그렇다고 표시하고 합쳐 견주지 않는다.
- **LLM**: 쓰지 않는다.
- **끝났다는 기준**: 계산마다 손으로 센 값과 같은지 시험한다(나누어떨어지지 않는 값, 값이 없는 칸, 부가세가 섞인 묶음, 옵션이 하나뿐인 상품).
- **한계**: 같은 상품이 다시 들어왔을 때 지난번과 달라진 칸을 보여 주는 일은 하지 않는다(무엇이 "같은 상품"인지 정하는 규칙이 먼저 필요하다).

## 4. 안 함

- 실제 메신저·알림·결제 연결, 실제 가수와 기획사 이름, 실제 사이트 수집.
- 딸린 도구마다 따로 서버를 세우는 일. 한 앱의 꼭지로 둔다(모으기만 파이썬 폴더).

## 5. 문서 이력

- v0.1 (2026-10-12): 처음 씀. 구현 전.
- v0.1 구현 뒤(2026-10-13): 문서의 결정은 그대로다. 구현하며 달라진 것 셋: 용어 사전은 공간별이다(공용 줄 = 본보기 공간). (여유)로 적은 LLM 제안 둘(처음 보는 출처의 칸 대응, 용어 후보)은 만들지 않았다. 모으기의 출력은 "본체의 초안"이 아니라 "모은 줄"이다: 줄은 먼저 모은 줄 표에 쌓이고, 사람이 고른 줄만 초안이 된다(3-2 의 "초안이 된 줄 수"는 그래서 사람이 누른 만큼이다. 12만 줄을 한꺼번에 검수함에 넣지 않으려는 것이다).
- 검토 뒤(2026-10-13): 3-3 의 한계 "읽지 못하는 표기는 승인하지 않는다"가 공용 15줄에서는 지켜지지 않았다. 씨앗이 그 줄들을 승인 상태로 싣고, 중국어 표기는 읽을 줄 아는 사람이 확인하지 않았다. 고치지 않고 화면과 README 에 그대로 적었다(제안 상태로 내리면 본보기 상품의 글 검사가 용어를 보지 않게 된다). 3-1 의 점검은 본체가 저장한 글 상태(확인 필요)도 읽는다. 3-4 의 조건이 없는 문의에는 상품을 고르지 않고 되묻는다.
- v0.2 (2026-10-13): 3-7 비교를 더했다. 구현 전. 사람이 "들어오는 자료를 견줄 수 있게 정리되면 좋겠다"고 해서 넣었다. 본체와 얼린 파이프라인은 건드리지 않고, 등록된 상품을 읽기만 하는 꼭지다.
- v0.2 구현 뒤(2026-10-13): 3-7 의 결정은 그대로다. 구현하며 정한 것과 알게 된 것 일곱.
  - 대표 하루당 값은 가장 짧은 기간 옵션에서 낸다(본체의 대표 판매가와 같은 옵션). 기간 옵션마다의 하루당 값도 함께 낸다. 대표 옵션의 기간이 서로 다른 지면(7일과 30일)을 같은 줄에 놓게 되는데, 기간을 맞추려고 값을 만들지 않고 값 옆에 어느 옵션에서 나눴는지 적는 데서 멈췄다.
  - "부가세가 섞이면 합쳐 견주지 않는다"는 이렇게 했다: 돈 잣대로 차례를 매길 때 별도끼리·포함끼리·적혀 있지 않은 것끼리 묶어 그 안에서만 차례를 매긴다. 나란히 놓을 때는 돈 잣대에 "좋은 쪽" 표시를 붙이지 않는다. 부가세가 적혀 있지 않은 것은 포함으로도 별도로도 치지 않는다.
  - "좋은 쪽" 표시는 방향이 분명한 잣대에만 붙인다. 작을수록 좋다고 본 것: 하루당 값, 유동인구 1,000명당 값, 한 개당 값, 마감·환불 일수, 굿즈의 판매가·최소 주문 수량·제작 기간. 클수록 좋다고 본 것: 유동인구, 운영 시간, 송출 횟수, 노출 시간. 붙이지 않는 것: 화면 넓이, 한 번 길이, 광고·케이터링의 판매가(서로 다른 기간·수량의 값이다). 이 방향은 재서 정한 것이 아니라 AI 가 정한 것이다.
  - 3-7 의 목록에 없던 잣대를 더했다: 하루 노출 시간(송출 횟수 × 한 번 길이), 전액 환불 일수, 케이터링의 한 개당 값(가장 적은 수량과 가장 많은 수량 옵션), 굿즈의 판매가·최소 주문 수량·제작 기간.
  - 3-7 은 "승인된 것"을 읽는다고 적었다. 상품 표에는 승인된 초안만 들어가므로 상품 표를 그대로 읽는다.
  - 지역 거르기는 위치(출장 지역) 글에 그 글자가 들어 있는지만 본다. 굿즈는 지역 칸이 없어 지역으로 거르면 빠진다.
  - 검토 뒤 고친 것(2026-10-13): "좋은 쪽"은 옵션에서 나눈 값이면 그 옵션의 기간(수량)이 같을 때만 붙인다(7일 옵션과 30일 옵션의 하루당 값은 견주지 않는다). 종류가 섞인 묶음의 판매가는 종류끼리만 차례를 매긴다. 같은 값은 같은 차례다. 같은 일수의 옵션이 둘이면 대표 판매가와 값이 같은 것이 대표다. 자세한 것은 `docs/DECISIONS.md`.
  - 본보기 공간에는 광고 지면이 3건(전광판·지하철·버스 하나씩, 부가세 별도 2·포함 1), 케이터링 2건, 굿즈 2건이 있다. 화면이 도는 것은 보이지만 같은 갈래끼리 견주는 보기는 없다. 보기 글을 더하려면 실제 호출로 녹화해야 해서 더하지 않았다.
