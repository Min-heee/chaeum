# 채움 — PRD v0.2

- 날짜: 2026-10-12 · 상태: 구현 전 · 만드는 사람: 1명(AI 코딩 도구 사용)
- 이 문서가 구현보다 먼저다. 평가 기준(7절)은 구현 뒤에 바꾸지 않는다. 바꾸게 되면 11절에 날짜와 이유를 적는다.

### 1. 한 줄 소개

공급처가 제각각으로 보낸 상품 소개 글(또는 단가표 그림·PDF)을 넣으면, 등록 양식의 칸이 채워진 초안과 "여기를 확인하세요" 표시가 나오고, 사람이 확인한 것만 양식 파일로 내려받는 도구. 그리고 그 채움이 얼마나 맞는지 사람이 확인한 정답으로 잰 기록.

### 2. 풀려는 문제

**누구의 일인가.** 팬 서포트 마켓(전광판 광고, 커피차, 굿즈를 파는 곳)의 운영자 한두 명. 매체사·업체가 보낸 소개 글, 단가표, 메신저 답을 읽고 등록 양식에 옮겨 적는다.

**무엇이 되풀이되나.**
- 같은 값이 글마다 다른 꼴로 온다. 운영 시간이 "05시~25시"로, 유동인구가 월 단위로, 크기가 m와 mm로, 값이 "150"(만원 생략)으로 온다.
- 값이 틀리면 결제 금액이 틀린다. 광고 지면은 수십만~수천만 원대다.
- 공개된 상품 페이지들을 살펴보면 흔한 등록 실수가 되풀이된다: 필수 옵션인데 고를 것이 없음, 종류와 갈래가 안 맞음, 안내 칸에 점 하나만 있음, 등록 대상이 아닌 글이 상품으로 올라감, 번역 칸에 모델의 혼잣말이나 한글이 섞임.

**이 도구의 자리.** 이런 마켓에는 보통 "양식 파일로 여러 상품을 한 번에 올리기"와 "자동 번역"이 이미 있다. 이 도구는 그것을 다시 만들지 않는다. 그 **앞**(제각각인 원문 → 양식 칸 채우기 + 의심 칸 표시)과 **뒤**(번역된 글과 구조를 검사)만 한다. 끝 산출물은 **채워진 양식 파일(CSV)** 이다.

### 3. 사용자와 흐름

**셀러(공급처)로 보기**
1. 가진 글을 그대로 붙여 넣는다. 여러 건이면 한 번에 넣는다(50건까지). 단가표 그림(JPG·PNG)이나 PDF 소개서는 파일로 올린다. AI가 먼저 글로 옮기고, 그 글이 같은 길을 탄다.
2. 칸이 채워진 초안을 본다. 칸마다 값, 원문의 근거 구절, 표시가 있다.
3. 못 찾은 칸을 직접 채우고 검수로 넘긴다.

**운영자로 보기**
1. 검수함을 연다. 두 갈래다: **확인 필요**(표시 있음)와 **바로 승인 가능**(표시 0개).
2. 한 건을 열면 왼쪽 원문, 오른쪽 칸. 값에 마우스를 올리면 원문 근거가 강조된다. 표시마다 사유 한 줄.
3. 승인 / 고쳐서 승인 / 반려(사유 코드 필수). 누가 무엇을 언제 바꿨는지 남는다.
4. 승인된 상품에 영어·중국어(간체) 제목과 요약이 붙는다. 글 검사에 걸리면 "글 확인 필요"로 남는다.
5. 승인된 것을 양식 파일(CSV)로 내려받는다.
6. 사람이 고친 값은 "정답 후보"로 쌓인다. 성적표에서 "가장 자주 고친 칸"으로 보인다.

화면은 "셀러로 보기 / 운영자로 보기"를 전환한다. **로그인과 권한은 없다.**

**처리 단계** (뽑기는 LLM, 맞추기와 따지기는 코드)

| 단계 | 누가 | 하는 일 |
|---|---|---|
| 접수 | 코드 | 글자 정리, 길이 제한, 같은 글이면 기존 건을 돌려줌 |
| 글로 옮기기 | LLM 1회(그림·PDF일 때만) | 파일을 글로 옮긴다. 초안에 "원본과 대조 필요" 표시가 붙는다. 파일 자체는 저장하지 않는다 |
| 뽑기 | LLM 1회 | 종류(광고 지면/케이터링/굿즈/**등록 대상 아님**)와 칸별 {원문 그대로, 읽은 값, 근거 구절}. 없으면 "없음" |
| 맞추기 | 코드 | 금액→원, 크기→m·mm, 시간→24시간제+다음 날 여부, 월 유동인구→하루, "1주"→7일 |
| 따지기 | 코드 | 근거가 원문에 있나, 코드가 읽은 값과 모델이 읽은 값이 같나, 범위, 필수 칸, 구조 규칙 |
| 갈래 | 코드 | 표시 0개면 "바로 승인 가능", 아니면 "확인 필요" |
| 검수 | 사람 | 승인·수정·반려 |
| 글 만들기 | LLM 1회 | 영어·중국어 제목·요약. 숫자는 자리표시(`{price}`)로만 쓰고 코드가 넣는다 |
| 글 검사 | 코드 | 자리표시 보존, 자리표시 밖 숫자, 한글 섞임·빈 칸, 혼잣말·머리말 흔적, 용어집 표기 |

확신도는 모델에게 묻지 않는다. 위 검사 신호로 만들고, 점수 대신 **사유 코드**를 남긴다.

### 4. 범위

**꼭**
1. 접수: 글 붙여 넣기(한 건, 여러 건 50건까지)와 그림·PDF 올리기(파일은 저장하지 않고 옮긴 글만 남긴다).
2. 종류 셋. 광고 지면은 깊게(칸 12개), 케이터링·굿즈는 얕게(칸 4~5개).
3. 뽑기 → 맞추기 → 따지기 → 갈래 → 검수 → 등록. PostgreSQL 작업 줄(집기·임대·재시도·죽은 작업).
4. 검수 API와 화면: 승인, 고쳐서 승인, 반려, 다시 돌리기, 변경 기록. 동시에 누르면 한쪽은 409.
5. 구조 규칙: 필수 옵션 0개, 종류와 갈래 불일치, 자리 채움 글자, 등록 대상 아님.
6. 영어·중국어(간체) 제목·요약 생성 + 글 검사 5종 + 1회 재시도.
7. 승인된 상품을 양식 꼴 CSV로 내려받기. 칸 이름 대응표(양식 맞춤 파일)를 바꾸면 다른 마켓의 양식 꼴로 나온다.
8. LLM 공급자 인터페이스 하나에 구현 셋: 실제 호출 / 녹화 재생 / 시험용.
9. 정답 세트 130건(연습 40 / 개선 중 안 여는 60 / 얼린 뒤: 실제 공개 자료 20 + 손으로 쓴 10), 전부 사람이 확인. 평가기, 방식별 비교표, 주입 시험.
10. 호출마다 비용·시간 기록, 실행 전 비용 어림(`--dry-run`), 상한(`--max-usd`).
11. 공개 시연(실제 API와 DB). 보기 글은 미리 받아 둔 실제 응답으로 바로 뜨고, **방문자가 직접 넣은 글·그림에는 진짜 LLM이 돈다**(하루 전체 건수 상한, 글 길이·파일 크기 상한, 가장 작은 모델, 키 자체의 지출 한도. 상한을 넘으면 "규칙만" 길로 내려가고 그렇게 표시한다). 로컬 실행도 진짜 LLM.
12. `npm run verify`(시험·타입·린트·빌드·녹화 재채점), README, `docs/`.
13. 번역 검사 API: 이미 번역된 제목·요약을 넣으면 글 검사 결과를 돌려준다. 자동 번역이 이미 있는 마켓이 그 결과를 검사하는 데 쓴다.

**여유 되면 (순서대로)**
1. 중간 크기 모델로 최종 세트를 한 번 더 돌려 칸별로 견주기.
2. 바로 승인 줄에서 무작위 표본을 뽑아 검수함에 섞기.
3. GitHub Actions에서 `npm run verify`.
4. 다른 회사 모델 공급자 구현(실제 호출로 잰 뒤에만 넣는다).

**안 함 (이유)**
- 양식 파일 대량 올리기, 여러 언어 전체 번역: 이런 마켓에 이미 있는 기능이다. 다시 만들지 않는다.
- 웹 수집(크롤링): 내가 만든 가상 페이지를 내가 읽는 것은 크롤링 경험이 아니다. 실제 사이트는 어떤 형태로도 긁지 않는다.
- 로그인·권한·결제·주문·정산: 등록 전 단계만 다룬다.
- 주소→좌표: 바깥 유료 API가 필요하다. (그림 읽기는 v0.2에서 범위에 넣었다. 따로 글자 인식 엔진을 두지 않고 모델에 그림을 그대로 넘겨 글로 옮긴다.)
- 에이전트, 벡터 DB, ORM, Redis, 별도 대기열 서버: 풀 문제에 필요 없다. 이유는 `docs/DECISIONS.md`.
- 일본어 등 내가 읽지 못하는 언어의 글 생성.

### 5. 자료

- 저장소와 시연에는 가상 마켓 "응원장터"(가칭)와 **직접 만든 합성 자료**만 쓴다. 실제 마켓의 글·값·사진·필드 이름을 가져오지 않는다. 어긋남의 **종류**(표기가 제각각인 꼴)만 가상 값으로 다시 만든다.
- 가수·그룹·매체사·업체 이름, 값, 규격은 전부 지어낸다. 지하철역·동네 이름은 실제 지명을 쓴다(공공 지명).
- **실제 자료 세트**: 공개된 매체·업체 소개 글과 단가표를 사람이 한 건씩 골라 가져온 20건으로도 잰다. 남의 글이므로 저장소에 원문을 넣지 않고, 출처 주소와 점수만 싣는다. 그래서 다른 사람이 이 세트로 다시 돌려 볼 수는 없다.
- 화면 맨 위에 늘 적는다: "가상 마켓 · 합성 자료 · 보기 글의 AI 답은 미리 받아 둔 실제 응답, 직접 넣은 글은 실제 호출".

### 6. 30초·2분 시연 대본 (가입 없음, 주소 하나)

**30초**
| 시간 | 하는 일 | 보이는 것 |
|---|---|---|
| 0:00 | 주소를 연다 | 설명 페이지가 아니라 작업 화면. 왼쪽에 보기 글이 이미 들어 있다 |
| 0:05 | "이 글로 초안 만들기" | 오른쪽 칸이 채워진다. "05시~25시"가 "05:00~다음 날 01:00"으로. 두 곳에 노란 표시와 사유 |
| 0:20 | 값에 마우스를 올린다 | 왼쪽 원문에서 근거 구절이 강조된다 |

**2분** (이어서)
| 시간 | 하는 일 | 보이는 것 |
|---|---|---|
| 0:35 | 보기 글을 "메신저 말투" 또는 "중국어 섞인 문의"로 바꿔 다시 | 꼴이 다른 글에서도 같은 양식이 채워진다 |
| 0:55 | 검수함 | 미리 들어 있는 건 + 방금 것. 사유별로 묶임. "등록 대상 아님"으로 걸린 건도 있다 |
| 1:10 | 한 칸의 값을 고쳐 승인 | 규칙이 서버에서 다시 돈다. 상태가 바뀌고 변경 기록 한 줄 |
| 1:25 | 상품 보기 | 영어·중국어 제목과 요약. 숫자는 같은 값. 글 검사 5종 결과 |
| 1:35 | "양식으로 내려받기" | 채워진 CSV 한 줄 |
| 1:45 | 성적표 | 방식별 비교표, 안 여는 세트·손글 세트 점수(따로), 틀린 건 목록, 건당 비용·시간 |
| 1:55 | API 탭 | 방금 누른 것과 같은 일을 하는 curl. 작업 공간 번호가 들어 있어 복사하면 그대로 돈다 |

자기 글을 직접 넣거나 그림·PDF를 올리는 칸도 첫 화면에 있다. 이때는 진짜 LLM이 돈다(하루 상한 안에서). 상한을 넘었거나 호출이 실패하면 "규칙만으로 뽑았습니다. AI를 거치지 않았습니다"라고 결과 위에 크게 적고, 로컬에서 돌리는 명령을 옆에 둔다.

### 7. 평가 — 기준을 먼저 적는다

**정답 세트 (네 묶음, 점수를 합치지 않는다)**

| 묶음 | 건 | 원문을 쓴 것 | 정답 | 쓰임 |
|---|---|---|---|---|
| 연습 | 40 | AI | 코드가 먼저 정한 값을 사람이 원문과 대조 | 프롬프트·규칙을 고칠 때 본다. 바깥에 내세우는 숫자에 쓰지 않는다 |
| 안 여는 세트 | 60 | AI | 위와 같음 | 고치는 동안 열지 않는다. 얼린 뒤 한 번, v1과 최종을 함께 돌린다 |
| 실제 자료 | 20 | **남이 쓴 공개 글**(사람이 골라 가져옴) | 사람이 직접 | 파이프라인을 얼린(태그) **뒤에** 모은다. 원문은 저장소에 넣지 않는다 |
| 손글 | 10 | **사람이 직접** | 사람이 직접 | 얼린 뒤에 쓴다. 실제 자료에 드문 함정을 채운다. 커밋 시각이 순서의 증거다 |

- 합성 두 묶음은 정답을 코드로 먼저 정하고 원문을 나중에 쓴다. 정답 자체가 모델에서 나오지 않게 하기 위해서다. 실제 자료와 손글은 사람이 원문을 보고 정답을 직접 적는다.
- 사람 확인은 한 번에 30건 안팎씩 나눠 한다. 건마다 걸린 시간과 고친 칸 수를 남긴다. 다 본 뒤 무작위 10건을 하루 뒤 다시 보고 처음 판정과 같은 수를 적는다.
- 확인하지 않은 건은 평가에서 뺀다.
- 평가 뒤 모델과 정답이 어긋난 건은 다시 본다. 정답이 틀렸으면 정답 세트 버전을 올리고 몇 건을 왜 고쳤는지 적는다.

**일치 기준**
- 맞춘 뒤의 값끼리 비교한다. 금액은 원 단위 정수가 같아야 맞음. 크기는 1% 이내. 시간은 시작·끝·다음 날 여부가 모두 같아야 맞음. 하루 유동인구는 5% 이내.
- 이름 칸은 공백·괄호·대소문자를 정리한 뒤 같아야 맞음. 포함 관계는 틀림.
- 목록 칸(기간 옵션 등)은 (키, 값) 쌍의 집합이 완전히 같아야 맞음.
- 자세한 것은 `docs/EVAL-SPEC.md`. 뼈대 커밋에 함께 넣고 그 뒤로 바꾸지 않는다.

**앞에 내세울 지표 여섯 (분자 / 분모)**

| 지표 | 분자 | 분모 |
|---|---|---|
| 칸 정확도(칸별) | 정답과 일치한 칸 | 정답에 값이 있는 칸 |
| 지어낸 값 | 정답이 "없음"인데 값을 낸 칸 | 정답이 "없음"인 칸 |
| 전부 맞은 문서 | 모든 칸이 맞은 문서 | 전체 문서 |
| 바로 승인 줄과 그 안의 틀린 것 | 표시 0개인 문서 수 / 그중 틀린 칸이 있는 문서 수 | 전체 문서 / 표시 0개인 문서 |
| 검사기 포착·헛경보 | 표시가 붙은 틀린 칸 / 표시가 붙은 맞은 칸 | 틀린 칸 전체 / 맞은 칸 전체 |
| 건당 비용·시간 | 호출 비용 합 / 걸린 시간 가운데값·95번째 | 문서 수 |

종류 분류 정확도, 놓친 값, 글 검사 통과율은 `docs/EVALUATION.md`에 싣는다.

**비교표** (같은 문서, 같은 호출): 규칙만 / LLM만(모델이 읽은 값 그대로) / LLM 뽑기 + 코드 맞추기. 규칙이 이긴 칸이 있으면 그대로 싣는다.

**주입 시험** (LLM 비용 0): 정답 값과 번역 글을 일부러 망가뜨린다(0 하나 더, m와 mm 뒤바꿈, 없는 근거, 기간이 길수록 싸지는 값, 혼잣말 넣기, 용어 바꾸기, 자리표시 지우기, 한글 섞기). 종류별로 검사기가 잡은 수 / 넣은 수를 낸다. 못 잡은 종류는 한계에 적는다.

**개선**: 2~3회. 한 번에 한 가지만 바꾸고 연습 세트에서 건별 나아짐·나빠짐을 본다. 버린 시도도 `docs/EVAL-LOG.md`에 남긴다.

**이 프로젝트가 성공이라고 말할 조건** (못 미쳐도 그대로 싣는다)
1. 모르는 사람이 주소 하나로 2분 안에 6절 대본을 끝까지 해 볼 수 있다.
2. 저장소를 받아 명령 일곱 줄로 로컬에서 진짜 LLM으로 돈다.
3. 정답 130건 전부에 사람 확인 기록이 있다.
4. 위 여섯 지표가 안 여는 세트, 실제 자료 세트, 손글 세트에서 따로, 분자/분모와 함께 나와 있다.
5. `npm run verify`가 키 없이 통과한다.
6. 방문자가 직접 넣은 글이 공개 사이트에서 진짜 LLM으로 처리된다(상한 안에서).

목표 숫자는 일부러 정하지 않는다. 기준선이 없는 채로 정한 목표는 근거가 없다.

### 8. 정직성 원칙과 한계

**숫자를 쓰는 법**
- 잰 것만 쓴다. 모든 비율 옆에 분자/분모를 쓴다.
- 묶음별 점수를 합치지 않는다. 연습 세트 점수는 바깥에 내세우지 않는다.
- 전후 비교는 같은 문서의 "나아짐 ○건 / 나빠짐 ○건"으로 한다.
- "○건 중 0건"을 "오류율 0%"라고 쓰지 않는다.
- "규칙만 → LLM" 차이를 "개선"이라고 부르지 않는다. 기준선 규칙을 대충 짤수록 차이가 커지는 숫자다.

**먼저 밝히는 한계**
- 대부분 합성 자료다. 그 원문은 AI가 썼고, 읽는 것도 같은 회사의 모델이다. 실제 자료 세트는 20건뿐이고 원문을 공개하지 못한다.
- 정답을 확인한 사람이 한 명이다. 두 사람의 일치도는 없다.
- 건수가 작다(60건이면 90% 근처에서 ±7.6%p).
- "안 여는 세트"는 약속이지 잠금장치가 아니다. 진짜 장치는 얼린 뒤에 모은 "실제 자료 세트"와 "손글 세트"다.
- 문제(함정 목록)를 낸 쪽과 푸는 쪽이 같은 편이다.
- 공개 사이트에서 보기 글의 AI 답은 녹화본이다. 직접 넣은 글은 하루 상한 안에서 실제로 호출한다. API·DB·작업 줄·규칙·승인은 늘 실제로 돈다.
- 공개 사이트에는 계속 도는 작업자가 없다. 요청이 작업을 굴린다. 따로 도는 작업자는 로컬에서만이다.
- 중국어 글의 자연스러움은 내가 판단하지 못한다. 코드 검사가 통과했다는 것까지만 말한다.
- 실제 서비스에 적용한 것이 아니다. 시연이다.
- 인증, 크롤링, 좌표, 결제가 없다. 그림·PDF는 모델이 옮긴 글에 기대므로, 옮기다 틀린 것은 사람이 원본과 대조해야 잡힌다. 다른 회사 모델로는 재지 않았다.

### 9. AI 사용 방식

- 이 문서의 초안과 코드는 AI 코딩 도구(Claude Code)가 쓴다. 무엇을 만들지는 사람이 정했고, 범위·구조·일치 기준은 AI가 낸 안을 사람이 읽고 확정한다.
- 사람이 맡는 일(계획): 합성 정답 100건 확인, 실제 자료 20건 모으기와 정답 쓰기, 손글 10건 쓰기, 회차마다 무엇을 고칠지와 채택·버림, 모델과 비용 결정.
- 공개 전에 사람이 직접 "칸 하나 더하기"를 해 보고 그 커밋을 남긴다.
- 위 가운데 실제로 하지 못한 것은 README에 그대로 적는다.

### 10. 열린 질문

1. 가장 작은 모델로 충분한가, 칸에 따라 무너지는가 → 연습 세트에서 재 보고 정한다.
2. 종류와 칸을 한 번에 뽑는 것과 따로 뽑는 것 중 어느 쪽이 나은가 → 종류가 셋뿐이라 한 번으로 시작한다. 종류 정확도를 따로 재고, 낮으면 연습 세트에서 한 번 견준다.
3. 어느 표시를 "확인 필요"의 사유로 삼을 것인가(헛경보와 놓침의 균형) → 연습 세트로 정하고 얼린다.
4. 무료 호스팅과 무료 DB의 한도로 2분 대본이 끊기지 않는가 → 뼈대 직후에 먼저 올려 본다. 안 되면 구조를 바꾼다.
5. (v0.2에서 정함) 방문자 글에 진짜 LLM을 연다. 남은 질문은 하루 상한을 몇 건으로 둘지다 → 실제로 잰 건당 비용을 보고 정한다.
